## 설명 보완의 재확인

단순 수치 표시와 별도로 실제 답변을 읽고 관측·판정과 대조했다.

- 결제: CPU 95%·메모리 90%의 의미와 CPU 작업 패턴·메모리 추세/힙 자료 점검 방향을 설명했다.
- 결제 CPU 고정 사례: 89.5%는 정상 기준(<80%)을 벗어나 CPU 점검이 필요하지만, 런북의 CPU >90%라는 증설 조건은 불충족이라고 설명했다. 메모리 55%는 정상 범위로 구분했다.
- 캐시: 메모리 사용 증가 관련 관측과 런북을 해당 서비스에 연결했다.
- 인증: CPU·메모리가 정상 범위여도 지연·커넥션 풀 알림을 추가 확인하도록 설명했다.
- 게이트웨이: 자원 수치가 정상이어도 타임아웃·네트워크 알림을 근거로 통신 구간 점검을 안내했다.
- 로그: 디스크 알림을 근거로 실제 용량과 로그 증가를 점검하도록 설명했다. CPU 문제로 바꾸지 않았다.
- 정상 웹 서버: 조회한 항목의 정상 상태를 설명하고 DB 장애 런북을 붙이지 않았다.
- 부분 회복: 남아 있는 메모리·알림을 점검하도록 안내했다.
- 정상 1회: 일시적인 정상화 가능성과 추가 관측 조건을 설명했다.
- 복구·재발: 정책상 복구와 실제 사용자 요청 성공을 구분하고, 재발이 같은 원인임을 단정하지 않았다.

POST 진단 8건은 실제 관측값과 표시 수치를 대조했다. SSE 1건은 최종 검증 통과·설명 출력·검증 전 AnswerToken 0건을 확인했다.
현재 SSE 최종 이벤트에는 관측 metadata가 포함되지 않아 POST와 같은 metadata 대조로 설명하지 않는다.
미수집 로그 분석·재시작·롤백 완료를 주장하는 표현은 확인한 답변에서 발견하지 않았다. 이는 모든 표현·질문의 정확성을 증명하는 검사는 아니다.

## 확인 범위의 한계

- 모든 모니터링은 샘플 JSON·합성 시나리오다. 실제 운영 장애 원인·복구 정답률을 측정하지 않았다.
- 복구 시나리오는 관측 시각을 10초 간격으로 제공한다. 실제 시간으로 5초씩 기다리며 운영 서버를 측정한 것은 아니다.
- stale/future/조회 실패·재시작 등의 예외는 자동 검사와 고정 입력으로 확인했다. 실행 중인 실제 운영 시스템에 장애를 주입하지 않았다.
- CPU 89.5% 검사는 실제 LLM을 사용하지만 MCP 통신은 고정 입력으로 대체했다.
- 설명은 검증된 관측·제공 런북 범위에 한정한다. 자유로운 근본 원인 분석을 검증했다는 뜻은 아니다.
- 제공 API·LangSmith 실제 연결은 미검증이다. PDF·PPT는 갱신하지 않았다.
