# AI Mini Project

**조사 대상 검증과 근거 기반 응답 검증을 통한 운영 장애 대응 에이전트 개선**

- **선택 과제:** 1번 - Base AI Agent 기능 개선/추가
- **초안 제출:** 2026년 10월 20일 17:00 (KST), GitHub README에 진행 계획 작성
- **현재 상태:** 제공 스켈레톤 실행 및 원본 반복 검증 완료. 핵심 개선 기능은 구현 예정입니다.
- **저장소:** https://github.com/likefool1714/ai-miniproject

## 1. 프로젝트 목적

운영 장애를 조사하는 에이전트가 **사용자가 요청한 서비스를 빠짐없이 조사하고, 실제 수집한 근거를 바탕으로 답변하도록** 개선합니다.

제공 코드의 기본 실행과 응답 생성은 작동했습니다. 그러나 실제 모델로 반복 검증한 결과, 조사 대상의 임의 대체·복수 대상 누락·조회하지 않은 로그를 분석했다고 표현하는 문제가 재현됐습니다. 이 문제를 해결하는 두 기능을 구현하고 같은 입력으로 개선 전후를 비교합니다.

> 이 저장소는 진행 계획 초안과 개선 전 검증 기록입니다. 아래의 개선 기능·After 수치·최종 발표자료는 아직 완료되지 않았습니다. RAG는 후속 확장 후보이며 현재 구현한 기술로 기재하지 않습니다.

## 2. 현재 스켈레톤의 기능과 처리 흐름

```text
웹 채팅 → FastAPI → 요청 분류
  ├─ 일반 대화 → 이력 기반 답변
  └─ 장애 조사 → 계획 → 작업 필터링 → MCP 모니터링 조회
               → 런북 추가 조회 → 필요시 분석
               → 답변 작성 → 형식 검사 → 최종 답변
```

| 현재 기능 | 내용 |
|---|---|
| Vue 웹 채팅 / SSE | 입력, 처리 단계, 답변 토큰과 최종 답변 표시 |
| LangGraph 처리 흐름 | 분류·계획·조사·재계획·분석·작성·검증 노드 연결 |
| MCP Tool / Resource / Prompt | 모니터링 조회, 대응 매뉴얼 조회, 표준 조사 절차 제공 |
| 모니터링 / 런북 | 등록 서비스 6개와 장애 대응 매뉴얼 6개 사용 |
| SQLite 대화 저장 | thread별 사용자·에이전트 메시지 저장 |
| 모델 교체 | fake / Ollama / API 백엔드 지원 구조 |
| 의존성 주입 / 재시도 / 추적 | 제공 코드의 의존성 번들, 일시 오류 재시도, LangSmith 연동 지점 |

현재 모니터링은 JSON 샘플에 난수를 더한 데모입니다. 실제 운영 인프라에 연결하거나 서비스 재시작·롤백을 실행하는 기능은 없습니다.

## 3. 개선 전 실행·교차 검증 결과

Python 3.12와 Ollama 기본 모델 `qwen3:0.6b`(분류·계획), `qwen3:8b`(답변)로 **6개 시나리오를 각 3회, 총 18회** 실행했습니다. API/SSE 이벤트, 실제 조회 대상, 최종 프롬프트와 답변을 대조하고 웹 화면에서도 미등록 서비스 문제를 확인했습니다. 제품 코드·데이터·실행 파일 29개가 제공 기준과 동일함을 확인했습니다.

| 시나리오 | 실제 관측 | 반복 결과 | 응답 시간 중앙값 |
|---|---|---|---:|
| 인사 | 일반 대화로 처리, 모니터링 미조회 | 3/3 | 1.3초 |
| 결제 서비스 명시 | 결제 서비스와 CPU 매뉴얼 조회 | 3/3 | 32.7초 |
| 서비스명 누락 | 확인 없이 `auth-service` 조사 | 문제 3/3 | 32.8초 |
| 미등록 `billing-service` | 요청 대상을 `auth-service`로 대체 | 문제 3/3 | 39.7초 |
| 결제·캐시 서비스 동시 요청 | 결제 서비스만 조사, 캐시 서비스 누락 | 문제 3/3 | 54.0초 |
| 게이트웨이 타임아웃 | 해당 서비스와 네트워크 매뉴얼 조회 | 3/3 | 36.9초 |

18회 모두 응답을 완료했지만, 응답의 정확성은 별도로 확인해야 했습니다.

- 결제 서비스 답변 3회 모두 실제 로그 조회 없이 **“로그 분석 결과 특이 패턴 없음”**이라고 표현했습니다.
- 복수 서비스 요청 한 건은 **CPU 89.5%가 90% 기준을 충족한다**고 잘못 비교했습니다.
- 분리한 검증기 검사에서는 수집값과 무관한 `CPU 999%` 문장도 길이·번호 형식을 맞추면 통과했습니다(3회).
- 별도 후속 대화 1건은 “그 서비스”의 대상을 이전 결제 서비스에서 인증 서비스로 바꿨습니다.
- 두 번째 후속 검사는 장시간 생성을 계속해 약 280초 후 **수동 중단**했고, 세 번째는 실행하지 않았습니다. 이 보조 검사를 18회 완료 결과와 구분합니다.

## 4. 개선할 기능과 완료 기준

### A. 조사 대상 검증 및 확인 대화

**문제:** 서비스 누락·미등록 시 임의 기본값을 사용하고, 모델 계획에 일부 대상만 있으면 빠진 서비스를 보충하지 않습니다.

**구현 계획**

- 등록 서비스 목록을 공통 모듈로 읽고 모델이 만든 조사 대상을 실행 전에 검증합니다.
- 서비스가 없거나 미등록이면 후보와 확인 질문을 반환하고, 확인 전에는 모니터링을 호출하지 않습니다.
- 명시한 대상 집합과 계획의 대상 집합을 대조해 복수 서비스의 조사 누락을 방지합니다.
- 확인 대기 상태에 원래 증상과 대상을 저장하고, 같은 thread의 후속 입력으로 조사를 이어갑니다.
- 일반 POST와 웹 SSE에서 동일한 동작을 보장합니다.

**완료 기준:** 대상 누락/미등록 시 잘못된 Tool 호출 0건, 복수 명시 대상 전부 조회, 확인 후 원래 증상을 유지한 조사 성공. 이는 동결한 평가셋의 목표이며 일반적인 정확도 보장을 뜻하지 않습니다.

### B. 근거 기반 답변 구조와 검증 강화

**문제:** 현재 검증기는 답변 길이와 번호 형식만 검사해, 수치 해석 오류나 실제 수행하지 않은 조사 완료 표현을 걸러내지 못합니다.

**구현 계획**

- 답변을 **확인된 사실 / 가능한 원인 / 권장 조치 / 추가 확인 사항**으로 구분합니다.
- 서비스명·CPU/메모리 값 등 자동 확인 가능한 항목을 실제 수집값과 대조합니다.
- 조회한 출처를 답변과 연결하고, 미조회 로그를 분석 완료로 표현하는 등의 문제를 탐지합니다.
- 검증 실패 시 제한된 재작성 후 실패·부분 답변 상태를 명시합니다. 최대 시도 도달을 무조건 합격으로 처리하지 않습니다.
- 모델별 생성량과 요청 전체 시간에 제한을 두고, 웹에 오류/중단 상태를 안내합니다.

**완료 기준:** 통제된 수치 오류·미수집 출처 주장을 탐지하고, 고정된 실제 모델 평가 입력의 결과와 실패 사례를 보고합니다. 자연어 답변의 모든 오류를 제거했다고 주장하지 않습니다.

### 선택 확장과 제외 범위

- **후속 확장:** 런북 의미 검색(RAG), 여러 증상에 대한 복수 매뉴얼 선택. 현재는 단일 결제·네트워크 사례의 매뉴얼 선택보다 대상/답변 오류가 직접 재현되어 우선순위를 낮췄습니다.
- **이번 범위 제외:** 신규 Research 서브에이전트 구조, 운영 조치 실행, 승인·재개 시스템, 회원가입/배포, 대규모 벡터 DB.

기술 예시를 모두 새로 구현하는 것으로 계획하지 않습니다. 재사용한 구조와 직접 변경한 부분을 구분하고 각 선택 이유와 실행 근거를 설명합니다.

| 비교 지표 | 현재 관측한 Before | After |
|---|---|---|
| 대상 누락 시 임의 서비스 조회 | 3/3 발생 | 미측정 |
| 미등록 요청의 다른 서비스 조회 | 3/3 발생 | 미측정 |
| 복수 요청의 조사 대상 누락 | 3/3 발생 | 미측정 |
| 결제 답변의 미수집 로그 분석 완료 표현 | 3/3 발생(수동 대조) | 미측정 |
| 시나리오별 전체 요청 지연 | 중앙값 약 1.3초 / 장애 조사 32.7-54.0초 | 미측정 |

**공정한 비교 방법**

1. 현재 18회 기록은 문제 탐색과 재현 증거로 보존합니다. 정식 Before/After에서는 난수 모니터링을 고정 스냅샷으로 대체해 기준 버전도 다시 측정합니다.
2. 동일 v2의 개선 전/후를 비교합니다. 원본 v1과 v2의 차이를 이번 개선 효과로 사용하지 않습니다.
3. 평가 입력을 동결하고 새로운 thread로 가능하면 각 3회 반복해 분자/분모와 중앙값을 저장합니다.
4. fake의 분기 검사, Ollama 실모델 결과, 제공 API 호환성 확인을 구분합니다. 서로 다른 모델의 차이를 기능 개선 효과로 해석하지 않습니다.
5. 코드의 `cost_usd`는 가상 단가 기반 추정치이므로 실제 청구 비용으로 제시하지 않습니다.

## 6. 기술과 직접 기여 범위

| 기술 | 제공 코드 | 이번 직접 작업 |
|---|---|---|
| FastAPI / Vue / SSE | 요청 처리와 채팅 UI | 확인 질문·검증 상태·오류 이벤트 연결 예정 |
| LangGraph | 분류/계획/조사/분석/작성 그래프 | 대상 확인 분기와 검증·종료 조건 개선 예정 |
| MCP | 실제 stdio Tool/Resource/Prompt 연결 | 검증한 대상만 조회하고 출처를 답변 근거와 연결 예정 |
| 의존성 주입 / 모듈화 | `SupervisorDeps` | 대상 판별과 응답 검사 로직을 교체·검사 가능한 모듈로 분리 예정 |
| SQLite | 대화 이력 저장 | 확인 대기 상태와 원래 요청 보존 예정 |
| 테스트·평가 | 교육용 시뮬레이션/회귀 질문 | 원본 반복 검증 실행기·증거 수집 완료, 개선 기능 검사와 전후 비교 예정 |
| LangSmith / API 백엔드 | 연동 지점 제공 | 이번 원본 검증에서는 추적 비활성화/API 미사용. 설정 후 확인 예정 |
| RAG | 현재 의미 기반 벡터 검색 없음 | 후속 확장 후보, 핵심 구현 완료 후 필요성 재평가 |

| 대상이 불명확하면 확인 | 잘못된 서비스 조사를 줄임 | 사용자 대화 턴 증가, 별칭·오타 처리 한계 |
| 코드로 수치/출처 검증 | 확인 가능한 오류를 재현 가능하게 검사 | 모든 자연어 주장이나 원인 추정의 진위를 판정할 수 없음 |
| 제한된 재작성 | 잘못된 응답을 고칠 기회 제공 | 모델 호출·지연 증가, 실패 상태 처리 필요 |
| 생성량/요청 시간 제한 | 장시간 대기 제어 | 답변이 잘릴 수 있어 부분 결과·중단 안내 필요 |
| 샘플 서비스 6개로 검증 | 작은 범위에서 구현·설명·반복 가능 | 실제 운영 장애 전체를 대표하지 않음 |

## 9. 로컬 실행

검증 환경은 Python 3.12입니다. 최초 한 번 `bash sh/setup_venv.sh`로 가상환경과 패키지를 준비합니다. Ollama에 `qwen3:0.6b`, `qwen3:8b` 모델이 필요합니다.

```bash
# 터미널 1: 이미 실행 중이면 중복 실행하지 않습니다.
ollama serve

# 터미널 2: 세션 DB를 삭제하지 않고 원본 백엔드 실행
LANGCHAIN_TRACING_V2=false LANGSMITH_TRACING=false \
LLM_BACKEND=ollama SUPERVISOR_VERSION=v2 .venv/bin/python server.py

# 터미널 3: 웹 채팅
.venv/bin/python -m uvicorn web_demo_server:app --host 127.0.0.1 --port 8600
```

웹: `http://localhost:8600` / 상태 확인: `http://localhost:8100/health`

제공 `sh/run_agent_*.sh`는 시작 시 `session.db`를 삭제합니다. 대화 보존 검증에는 위 직접 실행 방법을 사용합니다. 원격 API 검증 시 실제 키는 로컬 `.env`에만 저장합니다.
