# 선택 이유 및 개발 계획

## 목표

정보처리기사 공부 시간을 확보하면서 오늘/내일 구현과 검증을 끝내고, Day3 13:00 전에 제출 가능한 상태를 만듭니다. 기능 수보다 직접 설명 가능한 개선 두 가지와 재현 가능한 측정을 우선합니다.

## 과제 해석

PDF 실제 3/10페이지 기준으로 과제 1(기존 개선)과 과제 2(신규 개발) 중 하나를 선택합니다. 개선 예시는 실제 11/12페이지에 있으며 필수 구현 목록이 아닙니다. 별도 구두 안내로 개선 두 항목을 요구했다면 이 계획의 A/B를 두 항목으로 등록할 수 있습니다.

자료의 Day1 선택 마감은 17:00이지만, 이번 개인 계획은 사용자께서 말씀하신 **오늘 13:00 선택 완료**를 따릅니다. Day3의 날짜는 실제 수업 일정에 맞춰 확인하며, 날짜를 임의 확정하지 않습니다.

## 왜 기존 개선인가

새 주제는 도메인 데이터와 화면까지 새로 준비해야 합니다. 제공 예제의 운영 장애 대응 흐름을 유지하면 기존 UI와 MCP를 활용하면서 문제-개선-측정을 짧게 설명할 수 있습니다.

| 후보 | 장점 | 이번 판단 |
|---|---|---|
| 대상 서비스 확인 (예시 7) | 잘못된 대상 조사 방지, 동작/실패 기준이 명확함 | 핵심 A |
| 런북 RAG 검색 (예시 1) | 검색-근거-답변 흐름을 설명 가능, 정확도 비교 가능 | 핵심 B, 6개 문서로 제한 |
| 모듈화 (예시 2) | 코드 이해 및 변경 용이 | 바꾸는 부분만 분리, 별도 핵심 기능으로 과장하지 않음 |
| Research 서브에이전트 (예시 3) | 구조 확장 | 새 구조의 통합/검증 부담으로 제외 |
| 승인 노드 (예시 4) | 사람의 검토 반영 | 중단/재개/상태 저장/UI까지 필요해 제외 |
| 대화 요약 (예시 5) | 긴 대화의 입력 토큰 감소 가능 | 요약 품질과 장기 대화 검증 부담으로 제외 |
| LLM 평가자 (예시 6) | 정성 평가 자동화 | 평가자 변동/추가 호출 대신 정답 기반 평가 우선 |
| 데이터 보강 (예시 8) | 범위 확장 | 새 대규모 데이터 대신 평가 질문만 직접 작성 |

## A. 대상 서비스 확인

- 알려진 서비스의 정확한 이름이 있으면 해당 대상만 조사합니다. 복수 명시 시 모두 유지합니다.
- 서비스명 누락/미등록 시 후보를 안내하고 조사 전에 확인합니다.
- 같은 thread의 `payments-service` 같은 후속 응답을 원래 증상에 결합합니다.
- 이전 대화의 서비스명을 무조건 재사용하지 않습니다. 확인 대기 상태에서만 결합합니다.
- 확인 전에는 monitoring Tool을 호출하지 않습니다. 모델이 임의 대상을 넣어도 실행 전 검증합니다.
- 웹 SSE와 일반 POST에서 동일한 확인 동작을 보장합니다.

설명 예: “모델이 임의의 서비스를 고르면 잘못 조사할 수 있어서, 코드에서 등록된 대상 여부를 검사하고 없으면 사용자에게 확인합니다.”

## B. 작은 런북 RAG

- 제공 런북 6개를 우선 사용합니다. 문서 본문과 `incident_type`, 경로를 함께 인덱싱합니다.
- Ollama 임베딩 API와 로컬 벡터 인덱스/코사인 검색으로 시작합니다. 6개 규모에서는 별도 DB 서버를 두지 않습니다.
- 채팅 모델과 임베딩 모델은 역할이 다릅니다. 한국어 질의/영어 알림을 포함한 개발셋에서 임베딩 모델을 확인한 뒤 고정합니다.
- 사용자 증상 + 실제 모니터링 알림을 검색 질의로 사용합니다. 수집되지 않은 수치를 생성하지 않습니다.
- 검색된 런북의 본문을 MCP Resource로 읽고 답변 생성에 전달합니다. 검색만 붙이고 RAG 완료라고 하지 않습니다.
- 소스 경로/incident_type/유사도와 근거를 이벤트 또는 UI에 표시합니다.
- 임베딩 실패/빈 인덱스/낮은 점수는 명시적으로 처리합니다. 조용히 DB 장애로 단정하지 않습니다.

범위를 줄이는 선택: 평가셋으로 검증할 수 있는 단일 런북 검색부터 완료합니다. 복합 장애에서 다중 런북 검색은 한계/후속 개선으로 남깁니다.

## 일정과 중단 기준

| 구간 | 완료 기준 | 집중 작업 예상 |
|---|---|---|
| 오늘 13시 전 | 과제 선택, 등록 초안, 기준 버전 보존, 평가 질문 확정 | 30-60분 |
| 오늘 오후 | 원본 기동/Before 캡처 → 대상 확인 기능 및 후속 대화 | 2-3시간 |
| 내일 전반 | 인덱스/검색 → 그래프/MCP/UI 연결 | 2-3시간 |
| 내일 후반 | 동일 평가셋 비교, Ollama 및 API 확인, 실패 사례 정리 | 1.5-2시간 |
| 내일 마무리 | README/실측 표/7장 PPT, 코드 흐름 리허설 | 1-1.5시간 |
| Day3 오전 | 새 기능 추가 중단, 재현/링크/권한 확인, 13시 전 제출 | 버퍼 |

이는 집중 작업 예산이며 모델 설치/다운로드와 실모델 추론 시간이 추가될 수 있습니다. 오늘 원본 기동이 오래 걸리면 구조 확장/화면 꾸미기를 먼저 줄입니다. 내일 전반까지 RAG 연결이 안 되면 등록 계획을 수정하고 완료한 범위와 실패 원인을 명확히 남깁니다.

## 완료 정의

- 두 기능이 POST/웹에서 실제 동작합니다.
- 대상 누락/미등록/복수 대상/후속 확인/검색 실패를 다룹니다.
- Before/After 원시 결과와 집계, 모델/설정/환경/기준 SHA를 남깁니다.
- Ollama 실모델과 제공 API의 허용 모델로 핵심 시나리오를 확인합니다.
- 검색 향상이 없으면 그 사실과 실패 사례를 기록합니다.
- 제공 기능/직접 구현을 구분하고, 약 5분 동안 코드 흐름을 설명할 수 있습니다.
- 최종 PPT와 결과 보고서 링크가 실제로 열립니다.
