## 일반 장애 진단이 진행되는 순서

예시 질문: `payments-service 장애 원인과 CPU 런북 조건을 진단해주세요.`

1. **대상 확인** — `recovery_nodes.request_context_node`가 서비스명과 명령을 확인한다. 없으면 되묻고, “그 서비스”는 같은 대화의 저장 대상을 복원한다.
2. **계획·조회** — LangGraph의 `route → plan → gate → research`가 진행된다. 소형 모델은 분류·계획을 제안하고, 코드는 대상 누락·대체와 불필요한 분석 작업을 검사한다.
3. **근거 확보** — MCP Tool `get_monitoring_status`에서 상태·CPU·메모리·알림을 조회한다. 해당 증상 규칙에 맞는 런북을 MCP Resource로 읽는다. 부족한 런북은 한 번 추가 조회한다.
4. **저장·상태 비교** — `RecoveryStore.record`가 관측을 SQLite에 저장한다. `recovery.assess`는 이전 관측과 변화량·정상 횟수·자료 유효성을 비교해 복구 상태를 판정한다.
5. **모델의 제안** — `quality_llm.write_grounded`가 확보된 근거 안에서 원인 분류와 우선 확인할 런북 단계 ID를 선택한다. 예: 근거 M1, 원인 분류 cpu, 점검 단계 R1.2.
6. **검증·설명** — `grounding.validate_draft`가 출처·서비스 연결·분류·절차·중복 등을 검사한다. 반려 시 재작성은 한 번이며 다시 실패하면 모델 가설을 채택하지 않고 확인된 근거와 참고 절차로 제한한다. `render_answer`가 상태 해석·점검 방향·조건부 조치·수치·출처를 구성한다.

강의 기술은 LangGraph 흐름, MCP Tool/Resource/Prompt, Pydantic 구조화, 권위 게이트·Validator, 제한된 재작성에 연결된다. 서비스별 관측·실패·대상 보존은 직접 추가한 SQLite 저장 로직이다.

## 사실·해석·가설의 구분 예시

CPU 89.5%, 메모리 55%인 고정 입력 검사에서:

- **조회 사실:** 이 검사에 제공된 모니터링 값은 CPU 89.5%, 메모리 55%다. 운영 서버의 실제 측정값이라는 의미는 아니다.
- **정책에 따른 해석:** CPU는 정상 기준(<80%)을 벗어났고 메모리는 기준(<85%) 안이다. CPU 쪽 이상을 우선 점검할 근거가 있다.
- **런북에 따른 확인 방향:** 반복 호출·배치 작업 중복·배포/트래픽 변화를 확인한다. 현재 그중 어느 것이 원인인지는 모른다.
- **조건부 조치 판단:** CPU >90%라는 증설 수치 조건은 불충족이다. 90%를 넘더라도 지속 시간 등 다른 조건을 확인해야 한다.
