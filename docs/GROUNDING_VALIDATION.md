# 일반 진단·근거 검증 재점검

2026-10-20, v2, 로컬 Ollama qwen3:0.6b / qwen3:8b 기준이다.
PDF·PPT는 이 작업에서 생성하거나 갱신하지 않았다. 기존 PPT는 초안이다.

## 문제와 변경

이전 전체 경로 재확인에서는 결제 서비스 일반 진단이 실제로 읽지 않은 로그를 분석했다고 표현했다.
기존 Validator는 길이·번호 형식만 검사했고 재작성 세 번 후 실패한 답변도 강제 통과시켰다.
초안 토큰은 검증 전에 화면에 전달됐다. 증상이 없는 경우에도 DB 장애 런북을 기본으로 조회했다.

변경한 흐름은 다음과 같다.

1. 대상 서비스가 없으면 확인 질문으로 종료한다. 기본 서비스로 임의 조사하지 않는다.
2. MCP 모니터링의 대상·형식·시각을 검사한다. 증상에 맞는 런북을 추가 조회한다(최대 한 차례).
3. 유효한 관측 M1과 실제 읽은 런북 R1, 단계 R1.1을 근거 묶음으로 만든다. 모델 생성 analysis는 일차 근거에서 제외한다.
4. 모델은 근거 ID·원인 분류·런북 단계 ID만 JSON으로 제안한다. 자유 문장·임의 수치 필드는 허용하지 않는다.
5. 코드가 스키마·출처·서비스별 증상과 단계의 적용 가능성·누락·중복을 검사한다.
6. 실패하면 한 번만 재작성한다. 재실패·호출 오류는 검증 보류, 일부 자료 부족은 부분 검증으로 표시한다. 강제 통과는 없다.
7. 검증 이후 실제 관측값·시각·ID·조회 URI와 선택된 런북 원문으로 답변을 구성한다. 초안은 사용자에게 스트리밍하지 않는다.

CPU·메모리 런북의 명시적 수치 조건만 코드로 비교한다. CPU 89.5%는 `> 90%`에 불충족이다.
CPU 95%가 수치 조건을 충족해도 지속 시간·다른 조건을 수집하지 않았으므로 조치 실행을 확정하지 않는다.
로그·배포·트래픽·힙 덤프 미수집과 조치 미실행을 답변에 표시한다.

## 1. 자동 검사: 48/48

실행: `.venv/bin/python -m unittest discover -s tests -v`

기존 복구·변화·재발·SQLite·문맥·동시 요청 검사에 다음 항목을 더했다.

- 미수집 로그·CPU 999% 등이 포함된 자유 초안과 추가 필드 거부
- 존재하지 않는 근거·단계, 다른 서비스의 근거 혼용, 누락·중복 거부
- 정상 서비스에 장애 런북 기본 적용 방지, 복수 증상 런북 조회
- 초안 재작성 한 번 후 보류 및 재작성 성공 경로
- 작성 모델 연결 실패 시 보류, 생성 중 자료 만료 시 진단·복구 모두 보류
- null 모델 응답도 서버 오류 대신 제한된 재작성 후 보류, 잘못된 관측은 패턴 분석에서 제외
- 일부 서비스 조회 실패 시 다른 서비스의 근거 보존·부분 검증 표시
- 대상 없는 운영 요청 확인 질문, 새 요청의 대기 요청 교체, 감사 인사에 불필요한 조사 방지
- POST/SSE에서 검증 전 초안 미노출, 두 백엔드 JSON 요청 계약
- 분류·계획 모델 실패 시 확정된 대상으로 코드 경로 진행, 선택적 분석 실패 시 일차 근거 유지
- 프록시 시간 초과·잘못된 응답을 JSON 오류로 전달

요청 계약 검사는 모의 HTTP다. 제공 API 실호출 검증을 뜻하지 않는다.
실제 Ollama 연결 중 발견된 JSON 문법 호환 오류는 정규식의 `\\d`를 `[0-9]`로 바꿔 해결하고 실모델에서 재확인했다.

## 2. 같은 입력의 작성 방식 비교: 각 3회

실행: `.venv/bin/python -m eval.probe_grounding writer --repeat 3`

질문·CPU 89.5%/메모리 55%·알림·CPU 런북·qwen3:8b를 동일하게 제공했다.
관측 시각과 ID는 회차마다 새로 부여했다. 비교 전 write 함수가 커밋 3bb34a9의 함수와 AST가 같은지 검사했다.
전체 그래프 비교가 아닌 작성 단계 비교다.

| 항목 | 이전 자유 작성 | 개선 구조화 제안·검증·렌더링 |
|---|---|---|
| 완료 | 3/3 | 3/3 |
| 제안 검증 통과 | 기존 형식 검사만으로 의미 정확성을 확인할 수 없음 | 3/3, 보류 0 |
| CPU 89.5%의 >90% 조건 불충족 명시 | 0/3 | 3/3 |
| 작성 단계 중앙값 | 24.79초 | 6.68초 |

이전 답변 세 건은 모두 실제 수치 89.5%를 인용했다. 따라서 이를 임의 수치 조작 사례로 분류하지 않는다.
다만 확인하지 않은 반복 호출·배치 작업 패턴이 원인일 가능성이 높다고 쓰고, 89.5%에서 “임계치에 근접해 조치 필요”라고 썼다.
이를 CPU가 90%를 넘었다는 명시적 오답으로 과장하지 않는다. 개선 후에는 조건 불충족·원인 미확정·조치 미실행을 구분했다.
이 세 건의 이전 답변에서는 로그를 이미 분석했다는 표현이 재현되지는 않았다. 앞서 발견한 한 건과 구분한다.

시간 차이는 짧은 ID 선택·프롬프트 변경·추론 출력 비활성화(think=false)·출력 상한 1024를 포함한다.
이전 방식은 모델 기본 추론 설정, 평가 제한 60초, 개선 방식은 회당 40초/재작성 최대 한 번이다.
같은 자연어 추론의 단순 가속이나 일반 진단 정확도 상승률로 해석하지 않는다.

### 재검증 중 발견한 시간 초과

후속 전체 경로 재실행에서 기본 5단계 세 번은 통과했지만 추가 복수 서비스 요청이 장시간 생성에 걸렸다.
웹 프록시의 120초 제한이 백엔드 전체 제한 120초와 겹쳐 httpx.ReadTimeout이 500 오류로 노출됐다.
이 실패 실행은 노드별 시간을 계측하지 않아 어느 모델 단계가 얼마나 지연됐는지는 확정하지 않는다.
직접 확인한 오류는 프록시의 ReadTimeout이며, 생성 상한·실패 경로·프록시 처리를 함께 보완했다.
이 실패는 성공 건수에 합치지 않고 failed-rerun.txt와 before-timeout-fix-web-responses.json에 보존했다.
earlier-success-web-summary.json/extra-responses.json은 그보다 앞선 성공 실행 기록이다.

분류·계획·분석용 소형 모델은 think=false·출력 512 토큰·요청 20초로 제한했다.
분류·계획 모델 실패는 확정된 대상을 쓰는 코드 경로와 ModelFallback 이벤트로 처리한다.
선택적 분석 실패는 수집 근거를 대체하지 않는다.
웹 프록시는 135초로 여유를 두고 시간 초과·연결·응답 형식 오류를 JSON의 504/503/502로 전달한다.
이후 서버와 프록시를 재시작해 아래 전체 검사를 다시 수행했다.

## 3. 실제 웹·MCP·모델 전체 경로: 3회

실행 중인 8600 웹 프록시 → 8100 FastAPI → stdio MCP → 실제 Ollama로 검사했다.
합성 recovery-demo 자료를 사용했다.

실행: `.venv/bin/python -m eval.probe_grounding web --repeat 3`

- 첫 요청을 `payments-service 장애를 진단해주세요`로 보내 일반 LLM 진단을 실행했다. 세 건 모두 검증 통과했다.
- 서비스명을 생략한 후속 질문 네 번을 이어가며 장애 지속 → 부분 회복 → 정상 1회 보류 → 복구 확인 → 재발을 확인했다(판정 15/15).
- 각 대화의 관측은 5건이었다. 이력·보고서 조회는 건수를 늘리지 않았으며 Markdown 다운로드가 성공했다.
- 복수 서비스 일반 진단 1건과 정상 웹 서버 진단 1건도 검증 통과했다. 정상 웹 서버는 장애 런북을 조회하지 않았다.
- SSE 일반 진단 1건도 검증 통과했고 검증 전 AnswerToken은 0건이었다.
- 첫 일반 진단의 중앙값은 약 15.64초다. 빠른 후속 복구 경로의 시간과 구분한다.

일반 진단 6건의 통과는 **제한된 스키마·확보한 근거의 일관성 검사 결과**다. 실제 장애 원인을 여섯 건 모두 맞혔다는 의미가 아니다.
