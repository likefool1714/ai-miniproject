# 최초 기획과 현재 구현 대조·추가 버그 감사

> 아래는 수정 전 9fe3f02의 감사 기록이다. 이후 발견한 4종류를 수정했고 [수정·재검증·실제 화면](../results/bugfix-2026-10-21/README.md)에 결과를 남겼다. 아래 “미수정” 문구는 당시 상태를 뜻한다.

- 기준 버전: `9fe3f025131e9b21bfeb920b72ab461fef507947` (2026-10-21).
- 최초 기획의 기준은 대화에서 사용자가 최종 등록했다고 명시한 개선 5항목·기능 추가 5항목과 `docs/REGISTRATION_DRAFT.md`다. 초기에 논의한 후보와 미구현 후속 후보를 확정 범위로 섞지 않았다.
- 이번 작업은 감사다. 제품 코드·PPT를 수정하지 않았고 GitHub에 새 커밋을 올리지 않았다.

## 판단

주제와 기능 범위는 최초 등록을 유지한다. 별도 도메인이나 자동 운영 기능으로 바뀐 것은 아니다.
다만 기능이 존재하고 정상 흐름 검사가 통과했다는 사실만으로 모든 예외 조건까지 구현 완료라고 판단할 수 없다.
기존 67개 검사는 모두 통과했지만 추가 5사례를 두 차례 실행해 4종류의 문제를 재현했다.
POST/SSE 시간 초과는 같은 원인의 두 경로이므로 별개 버그 두 개로 세지 않는다.

## 최초 문구보다 구체화되거나 제한된 부분

1. **정상 2회·최소 5초 간격**: 연속 관측이라는 최초 요구를 실행 가능한 교육용 정책으로 구체화했다. 산업 표준이나 실제 서비스 복구 증거라는 뜻은 아니다.
2. **같은 대화의 서비스별 이력**: 최초 문구의 서비스별 저장을 대화별로도 분리했다. 새 조사/다른 대화에서는 이전 대화의 기록을 자동으로 합치지 않는다.
3. **자료 300초·재발 3600초·판정 500건·보고서 표 100건**: 저장·비교 범위의 제한이다. 무제한 조사·장애 재발 탐지라고 설명하면 부정확하다.
4. **근거 검증·설명 보완**: 원래의 자유 답변 대신 모델이 관측 근거 ID와 런북 항목을 제안하고 코드가 검사한다. 수치의 의미와 점검 방향도 설명한다. 등록한 복구 기능을 뒷받침하는 품질 보완이며 별도 주제로 변경한 것이 아니다. 자유로운 진단 표현·범위는 줄어드는 트레이드오프가 있다.
5. **재점검 경로는 코드 판정 중심**: 최초 진단은 모델 계획/진단 선택을 사용하지만 복구 재점검·이력·보고서는 모델 생성 없이도 처리한다. 모든 기능이 매번 LLM을 호출한다고 설명하지 않는다.
6. **확인된 미구현 후보**: 관련 서비스 자동 연쇄 조사, 배포·설정 변경 이력 수집, HTTP 기능 점검, 운영자 조치 메모, 자동 재시작·확장·롤백. 후보를 완료 기능으로 세지 않는다. 벡터 RAG·LLM-as-a-Judge를 새 구현으로 세지 않는다.

## 재현된 문제

### B1. 전체 요청 시간 초과가 관측 수집을 취소하면 정상 연속성이 끊기지 않음 — 우선순위 높음

- 재현: 최근 장애 → 정상 1회 → 모니터링을 기다리던 전체 요청 시간 초과 → 새 정상 관측 1회.
- 기대: 실패 이후 정상 1회로 다시 세어 부분 회복.
- 실제: 실패 기록이 없고 정상 횟수 2회로 복구 확인. POST와 SSE 모두 재현했다.
- 조건: 전체 요청 한도가 수집 도중 만료되는 경우다. 빠른 재현을 위해 한도를 0.03초로 주입하고 조회를 지연시켰다. 실제 120초를 기다린 실험이나 실제 제공 API 장애 검사는 아니다. 기본 15초 Tool 제한을 초과하는 모든 오류가 이 문제를 일으킨다고 일반화하지 않는다.
- 원인: server.py 169/231의 바깥 timeout이 취소를 일으키고, 171/234의 오류 응답 경로는 RecoveryStore.failed를 호출하지 않는다. recovery_nodes.py 96의 일반 Exception 처리는 취소 예외를 처리하지 못한다.
- 영향: '조회 실패가 끼면 정상 관측을 다시 센다'는 현재 보고서 설명과 불일치한다.
- 수정 방향: 실제 조사를 시작한 대상과 완료 여부를 추적하고, 해당 수집이 취소·시간 초과되면 같은 대화·대상에 실패 경계를 저장한다. 잠금 대기 중의 시간 초과나 이미 완료한 다른 조사를 무조건 실패로 표시하는 방식은 피해야 한다.

### B2. CPU·메모리의 true/false를 숫자로 받아 복구 판정에 사용함 — 우선순위 높음

- 재현: 정상 상태의 CPU=true, 메모리=false 자료를 10초 간격으로 두 번 전달.
- 기대: 백분율 자료 형식 오류로 거절/판단 보류.
- 실제: Observation이 각각 1.0%, 0.0%로 변환하고 복구 확인에 사용한다.
- 확인 수준: RecoveryStore/Observation에 잘못된 자료를 직접 넣는 단위 재현이다. 현재 합성 모니터링이나 실제 제공 API에서 이런 값을 관측했다는 뜻은 아니다.
- 원인: recovery.py 44~48에서 float 필드의 boolean 자동 변환을 금지하지 않는다.
- 수정 방향: 백분율 필드에서 bool을 변환 전에 거부한다. MCP 응답 스키마에서도 같은 검증이 필요한지 확인하고 정상 int/float 값은 허용한다.

### B3. 제외하라고 한 서비스까지 조사함 — 우선순위 중간

- 입력: `결제 서비스 말고 인증 서비스만 다시 확인해 주세요`.
- 기대: auth-service만 조회.
- 실제: payments-service와 auth-service 모두 조회·저장한다. 이는 의존관계 기반 연관 조사 기능이 아니라 대상 추출 오류다.
- 원인: recovery_nodes.py 22~29가 서비스의 등장 여부만 수집하고 제외/한정 표현을 해석하지 않는다.
- 수정 방향: 명확한 제외 표현을 반영하거나, 해석하기 어려운 경우 대상 목록을 확인한다. 전체 자연어를 정규식으로 완전히 해석할 수 있다고 주장하지 않는다.

### B4. 확인 질문에 자연스럽게 답하면 원래 재점검 요청이 일반 진단으로 바뀜 — 우선순위 중간

- 재현: 결제·캐시 복수 서비스 조사 → `그 서비스 복구됐어?` → 대상 확인 질문 → `결제 서비스 상태요`.
- 기대: 결제 서비스를 대상으로 대기 중이던 복구 재점검 계속.
- 실제: recovery_action=legacy, validation_status=validated인 일반 진단을 실행한다. 서비스 자체는 결제로 맞지만 원래 요청 종류를 잃는다.
- 원인: recovery_nodes.py 61~66에서 짧은 대상 답변에도 '상태'가 있으면 새 운영 요청으로 판단하고 pending을 취소한다.
- 영향: 불필요한 모델/런북 조회와 응답 흐름 변경. 추가 토큰·초 단위 지연은 이번 감사에서 따로 실측하지 않았다.
- 수정 방향: 짧은 대상 선택 답변과 새 완전한 명령을 구분한다. 기존 '새 전체 요청은 이전 pending을 교체' 검사도 유지해야 한다.

'처음 등록한 기능의 정상 흐름은 구현하고 검사했다. 추가 감사에서 시간 초과·자료 형식·대상 해석 예외를 발견했다'가 현재 근거에 맞다.
