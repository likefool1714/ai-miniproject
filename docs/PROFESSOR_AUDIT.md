검증일: 2026-10-20. 직전 공개 버전 c885d6c를 기준으로 코드·실행 결과·강의 요구를 대조했다.
PDF/PPT는 작성하지 않았다. 설명 준비는 [발표·코드 안내](DEFENSE_GUIDE.md)에 정리했다.

## 결론과 검증 범위

등록한 상태 비교·복구 확인·이력·재발·보고서 개선을 로컬에서 확인했다.
기존 검사에 없던 오류 세 가지를 재현하고 수정했다. 검사 통과를 무오류 보증이나 실제 운영 복구 정확도로 해석하지 않는다.
제공 API·LangSmith 실연결과 최종 PDF/PPT는 아직 미완료다.

## 기존 검사 밖에서 발견한 문제

기존 48개 검사를 다시 실행했을 때 모두 통과했다.
이후 조건을 바꾼 반례에서는 아래 문제가 재현됐다. 원문은 `results/professor-audit-2026-10-20/edge-cases-before.json`이다.

| 상황 | 수정 전 실제 결과 | 수정 후 요구·확인 결과 |
|---|---|---|
| 장애 → 정상 1회 → 조회 실패 → 새 정상 1회 | 정상 2회로 합쳐 recovered | 실패 뒤 정상 1/2회이므로 partial, 다음 새 정상에서 recovered |
| 복구 확인 → 조회 실패 → 예전 정상 관측 재전송 | 실패 기록 삭제·recovered | hold 유지·실패 보존, 예전 ID로 최근 실패를 해소하지 않음 |
| 장애 후 130개 새 정상 관측, 모두 300초 이내 | 실시간 recovered / 보고서 hold | 같은 500건 범위로 현재 판정, 실시간·보고서 모두 recovered |

수정은 다음과 같다.

- `recovery_continuity`: 마지막 조회 실패 시점의 관측 ID를 저장해 정상 횟수를 그 뒤부터 센다. 재시작해도 보존한다.
- 중복/과거 ID는 새 성공 조회로 처리하지 않고 최근 실패를 유지한다. ID 내용 충돌도 예전 원본 재전송으로 해소하지 않는다.
- 검증에 실패한 관측은 일반 진단의 근거 묶음에서도 제외한다.
- 잘못된 미래 시각 자료가 들어와도 후속의 정상 관측 처리를 영구적으로 막지 않는다.
- 실시간·보고서 판정은 모두 최근 최대 500건이다. 보고서 표만 100건으로 제한한다. 새 관측 추가 시 501건을 판정하는 경계도 수정했다.

전체 흐름 첫 일반 진단의 중앙값은 약 15.33초였다. 과거 고정 fixture의 ms 단위 복구 경로와 다른 측정이다.
추가 서비스 검사는 `service-coverage.json`에 기록한다. 결과 파일의 status가 passed인지 함께 확인해야 한다.
인증·게이트웨이·로그 서비스의 런북 선택과 수치 인용이 통과했고, 같은 대화에서 대상을 바꾼 뒤 “그 서비스”가 새 대상을 유지했다.
로그 서비스는 한국어 별칭으로 요청했으며 마지막 보고서 대상도 로그 서비스였다. 결제·캐시·웹 검사와 합쳐 등록 서비스 6종의 일반 진단을 확인했다.

### 추가 서비스에서 확인한 모델 한계

인증 서비스 첫 검사에서는 모델이 고른 원인가설의 근거·분류가 수집 자료와 일치하지 않아 두 번 반려됐습니다.
최종 응답은 검증 보류로 전환되어 미수집 원인 주장을 채택하지 않았습니다.
이를 차단된 모델 선택 실패로 기록하고 service-coverage-first-failure.json과 요약 파일에 보존했습니다.

## 과제·강의와 맞는 설명

3주차 미니프로젝트 PDF p.10은 기존 기능 개선을 허용하고 작성된 코드 설명을 요구한다.
p.11~12의 RAG·LLM-as-a-Judge 등은 개선 예시다. 이를 모두 새 구현했다고 말하지 않는다.
p.13의 완성도·전후 실측·기술 요소·한계 설명에 코드와 증거를 연결했다. 배점 획득을 보장하지 않는다.
p.5의 제공 API 실호출 단계는 아직 미검증이므로 과제 전체 완료로 표시하지 않는다.

2주차 Capstone의 Pydantic(p.31), 권위 게이트(p.148), 재계획(p.155), Validator와 제한된 재작성(p.165~167),
시간/반복 가드(p.170), 상태 저장 목적(p.209), 의존성 주입(p.219~222), 고정 평가 자료(p.245)를 적용했다.
SQLite 저장을 LangGraph 내장 Checkpointer 구현으로, 코드 검증을 LLM 심판 구현으로 설명하지 않는다.

## 발표에서 주장할 것과 남은 한계

“현재 수치만 보고 조언하던 흐름에 조사 이력과 정책 기반 복구 재확인을 추가했다.
모델 제안은 수집 근거로 검사하고, 실패·중복·미확인 자료에는 보수적으로 응답한다.”

정상 2회·5초·CPU80/메모리85·유효시간300초는 교육용 정책이다. 서비스 SLO나 실제 장애 복구 보증이 아니다.
임계값을 엄격하게 하거나 정상 횟수를 늘리면 확인이 지연된다. 관측 사이 상태와 사용자 결제 성공은 확인하지 않는다.
현재 모델 출력은 근거/분류/런북 단계로 제한해 표현력·원인 추론 범위를 줄인다.
후속 복구 경로의 속도 차이는 LLM 생략을 포함한다. 제공 코드의 데모 지연·모의 retry도 운영 성능으로 해석하지 않는다.
인증·다중 서버·장기 이력 정책·자동 운영 조치·의미 기반 RAG는 범위 밖이다.

검증 후에도 작성자 본인의 코드 이해는 별도로 확인해야 한다. [설명 안내](DEFENSE_GUIDE.md)의 다섯 함수를 실제로 따라 읽고,
예시 숫자에서 왜 해당 phase가 나오는지 말할 수 있는 상태를 발표 준비 기준으로 삼는다.
