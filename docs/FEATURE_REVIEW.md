# 추가 기능 전체 검토 — 제안이며 미구현

2026-10-21, 현재 제품 코드 `b25e050`과 원본 `d1043ff`, 과제 자료를 대조했다.
이 문서는 선택을 위한 설계안이다. 아래 새 기능은 아직 구현·검증하지 않았으며 제품 코드는 변경하지 않았다.

## 현재 완료 범위와 남은 일

- 로컬 Ollama 모드에서 현재 진단·관측 이력·변화 비교·복구 재점검·재발·보고서가 동작한다.
- 이력·비교·복구 판정 자체는 Python/SQLite 로직이며 LLM 백엔드와 분리되어 있다. 일반 진단에는 Ollama 모델을 사용한다.
- 과제 PDF 뷰어 p.5의 3-2는 개발 정리 후 API 백엔드로 전환해 테스트하는 단계다. 키 설정·서버 기동만으로 완료한 것으로 보지 않고 실제 진단·문맥·복수 대상·검증·스트리밍을 확인해야 한다.
- 후속 확인: 제공 키를 통한 실제 API 진단 POST 3건·SSE 1건과 복구·이력·보고서를 확인했다. [실제 결과](../results/api-2026-10-21/README.md). 아래 새 기능 후보는 여전히 미구현이다.
- LangSmith 실제 추적 확인, 최종 기능 기준 전후 실측 기록 정리, 코드 설명 준비, 최종 발표 자료·제출 정리도 남는다.
- 새 기능을 선택하면 그 기능을 로컬에서 먼저 완성·검증하고 API 모드를 최종 확인하는 순서가 적합하다.

## 기존 추가 기능의 성격을 다시 평가

원본에는 SQLite 대화 메시지 저장이 이미 있었다. 우리가 추가한 것은 서비스별 구조화된 관측·판정·대상/실패 상태 저장이다.
따라서 스켈레톤 대비 추가 구현은 맞다. 다만 이력·재점검·보고서 등은 운영 도구가 갖추어야 할 기본 기능이라는 관점도 타당하다.
기존 작업은 신뢰성과 연속 조사 기반으로 유지하되, 핵심 차별화 기능을 더 원한다면 **새 자료를 조사하거나 새로운 범위까지 판단하는 능력** 하나를 추가하는 편이 명확하다.

과제 p.10은 선택한 코드의 설명 가능성을 요구하며, p.13은 실제 동작·기술·실측·한계·발표를 평가한다. 새 기능의 개수나 독창성만으로 점수를 보장하지 않는다.

## 현재 코드에 없는 후보 비교

| 후보 | 현재와 다른 사용 능력 | 필요한 변경 | 주요 한계 |
|---|---|---|---|
| **서비스 의존관계 기반 연관 조사·영향 안내 (우선 추천)** | 한 서비스 요청에서도 호출 관계상 관련 서비스를 추가 조회하고 영향 가능 범위 제시 | 관계 JSON/MCP Resource, 조사 대상 확장 노드, 출처 연결·범위 제한 | 관계가 오래되면 잘못된 대상을 조사. 관계와 동시 이상만으로 근본 원인 확정 불가 |
| 최근 배포·설정 변경 이력 연계 | 장애 직전 어떤 변경이 있었는지 실제 조회 자료와 시간으로 연결 | 변경 이력 MCP Tool/Resource, 시각·서비스 매칭, 근거 D1 등 별도 표시 | 시간상 앞선 변경이 원인이라는 보장은 없음. 현재 배포 이력은 없어 샘플 또는 실제 연동 필요 |
| 읽기 전용 HTTP 기능 상태 확인 | CPU·메모리 외에 등록한 테스트 요청의 상태 코드·응답 시간을 확인 | 별도 점검 Tool, 허용 대상·타임아웃, 테스트용 엔드포인트, 결과 정책 | 테스트 요청 성공이 전체 기능 성공을 보장하지 않음. 현재 대상 서비스의 실제 URL은 없음 |

세 후보 모두 미구현이다. 일정과 설명 부담을 고려하면 핵심 하나를 선택하는 편이 적합하다.
앞서 제안한 운영자 메모는 편의·인수인계 기능 후보로 남기되, 새로운 조사 능력을 보여 주는 우선 후보는 위 첫 번째다.
벡터 RAG도 과제 예시에 있지만 현재 런북 6종에서의 검색 이점을 먼저 입증해야 한다. 이번에는 기존 진단과 차이가 직접 보이는 후보를 우선한다.
다른 수강생의 최신 등록표는 이번 검토에 포함하지 않았으므로 수강생 전체와의 중복 여부를 보장하지 않는다.

## 권장 기능의 구체적 범위

**기능명: 서비스 의존관계 기반 연관 서비스 자동 조사 및 영향 범위 안내**

예시 관계는 데모용 설정이다. 현재 인프라에서 자동 발견한 사실로 표현하지 않는다.

```text
등록된 예시 호출 관계: gateway-service → payments-service

질문: gateway-service 요청이 타임아웃 나요. 확인해주세요.

현재:
  gateway-service 조회 → 해당 서비스의 알림과 네트워크 런북으로 안내

추가 후 목표:
  관계 자료 조회 → gateway-service + payments-service 관측 조회
  → 각 서비스의 상태를 대조
  → 우선 점검 후보·영향 가능 범위·근거·미확인 부분 설명
```

payments-service에서도 이상이 관측되면 관련 부하를 우선 확인할 후보로 안내할 수 있다.
payments-service가 정상이거나 조회에 실패하면 그 사실도 표시하고, 해당 서비스가 원인이라고 채우지 않는다.
영향 범위는 등록된 관계에 따른 가능 범위이며 실제 사용자 피해 건수나 장애 전파 사실로 단정하지 않는다.

### 기존 기능과 구분

- 기존 복수 서비스 진단: 사용자가 A와 B를 직접 지정하면 각각 조회한다.
- 새 기능 목표: 사용자가 A만 지정해도 관계 자료에서 B를 찾아 추가 조사하고 연결된 근거를 설명한다.
- 기존 이력·재발·보고서: 관측 보존과 시간상 상태 변화가 중심이다.
- 새 기능 목표: 서비스 간 연결 관계와 조사 범위를 다룬다.

이는 하나의 기능을 구성하는 동작들이다. 대상 확장·비교·영향 안내를 각각 독립 기능으로 부풀려 세지 않는다.

### 설계·통합 지점

1. `data/service_dependencies.json`에 서비스 간 호출 관계와 출처·갱신 시각을 정의한다.
2. 정적 관계 자료는 MCP Resource로 제공하고, 실제 상태는 기존 모니터링 Tool로 조회한다.
3. LangGraph에 관계 조회·조사 대상 확장 단계를 추가한다. 모델의 제안에 관계 자료를 전달하고 허용 범위를 코드로 검사한다.
4. 요청 대상과 연관 조사 대상을 분리한다. “그 서비스”의 원래 대상이 연관 서비스 목록으로 바뀌지 않도록 한다.
5. 확장은 1단계·최대 3개 서비스로 제한하고 이미 방문한 대상·미등록 서비스·누락/오래된 관계를 처리한다.
6. 응답에 관계 출처와 각 서비스의 관측 근거를 연결한다. 관련 관계를 못 구하면 원래 대상의 단독 진단을 유지한다.

기존 상태 저장·복구 판정·검증을 기반으로 사용하되, 관련 서비스를 모두 장애나 근본 원인으로 취급하지 않는다.
새 전문 서브에이전트를 실제로 구현하지 않는 한 “멀티 에이전트를 새로 추가했다”고 설명하지 않는다.

### 전후 확인과 발표 포인트

- 같은 단일 서비스 질문에서 요청 대상·실제 조회 대상·조회 근거가 어떻게 달라지는지 비교한다.
- 관계 있음/없음, 연관 서비스 정상/비정상/조회 실패, 순환 관계, 범위 초과를 확인한다.
- 추가 조회 수·지연·토큰 사용과 관련 대상 누락 여부를 측정한다. 더 조사하므로 항상 빨라진다고 가정하지 않는다.
- 새로운 관계·동시 이상 자료로도 원인 인과관계를 확정하지 않는 한계를 설명한다.

## 등록용 문안 초안 — 아직 선택·구현 전

**[추가 기능] 서비스 의존관계 기반 연관 서비스 조사**

- 단일 서비스 장애 요청에서 등록된 호출 관계를 조회하고 관련 서비스 상태까지 추가 조사.
- 서비스별 관측 근거를 대조해 우선 점검 후보와 영향 가능 범위 안내.
- 관계 출처·조사 대상·판단 한계를 함께 표시하고 조사 범위를 제한.

이 안을 새 범위로 선택한 뒤에 구현 여부와 실제 결과를 갱신해야 한다. 현재 완료 기능으로 기재하지 않는다.
