# 한계와 트레이드오프

아래는 설계 시 예상한 한계입니다. 구현 후 실제 관측 결과와 구분해 갱신합니다.

| 선택 | 얻는 점 | 대가/한계 | 검증/후속 개선 |
|---|---|---|---|
| 대상 불명확 시 되묻기 | 임의의 서비스 조회 방지 | 사용자 턴 증가, 증상만으로 자동 확정하지 못함 | 불필요 조회와 해결 턴 수 동시 측정 |
| 등록 서비스 중심 검증 | 실행 가능한 대상 통제 | 별칭/오타/새 서비스 처리 한계 | 미등록 안내, 나중에 관리 가능한 별칭 설정 |
| 임베딩 의미 검색 | 다른 표현의 증상을 찾을 가능성 | 임베딩 준비/쿼리 지연, 검색 오류 | 개발셋 모델 고정, 평가셋 실측, 실패 명시 |
| 로컬 인덱스 | 별도 서버 관리 부담 감소 | 문서 증가 시 전체 비교 비용, 갱신/동시성 한계 | 문서 해시/모델명 캐시, 규모 확대 시 DB 검토 |
| 런북 6개 | 기간 내 데이터 검토와 설명 가능 | 실제 장애의 복합성/다양성을 대표하지 않음 | 혼합 증상 실패 사례, 다중 문서 검색 후속 |
| 한국어 질의 + 영어 알림 | 현재 예제 데이터 활용 | 언어 간 임베딩 매칭 품질에 좌우됨 | 한/영 표현별 결과 구분 |
| 유사도 점수 | 검색 순위와 기준을 노출 | 확률/정답 신뢰도가 아님, 임계값 임의 설정 위험 | 개발셋에서 기준 선택, 확률로 표시하지 않음 |
| 근거를 넣은 답변 | 매뉴얼 출처 확인 가능 | 생성 모델이 근거를 왜곡할 가능성 | 출처/수치 검사, 환각이 사라졌다고 주장하지 않음 |
| 기존 validate 유지 | 구조 변경 최소화 | 30자/번호 검사는 사실성 검증이 아님, 최대 시도 후 강제 통과 | 구조 검사와 정확성 평가를 별도 보고 |
| 로컬 개발 후 API 확인 | 로컬 반복 개발과 실제 백엔드 점검 | 모델마다 분류/계획/한국어 품질이 다름 | 대표 시나리오를 두 백엔드에서 별도 확인 |
| 샘플 모니터링 | 안전한 반복 실험 | 실제 운영 환경에서 검증되지 않음 | 데모 범위로 명시, 운영 적용은 별도 과제 |

본 프로젝트는 조사/권고를 제공하며 실제 서비스 재시작, 스케일링, 롤백을 수행하지 않습니다. 향후 운영 조치 기능을 넣는다면 별도의 승인/권한/감사 설계가 필요합니다.
