# 한계와 트레이드오프

아래는 설계 단계의 예상 한계이다. 구현 후 실제 관측한 실패 사례와 구분해 갱신한다.

| 선택 | 얻는 점 | 한계/대가 | 확인할 사항 |
|---|---|---|---|
| 대상 불명확 시 확인 | 임의 서비스 조회 방지 | 사용자 턴 증가, 별칭·오타·새 서비스 처리 한계 | 잘못된 조회 수와 해결 턴 수 동시 측정 |
| 명시 대상 집합 검증 | 복수 대상 누락 방지 | 모호한 간접 지칭은 단순 문자열 검사로 해결하기 어려움 | thread 상태 활용, 모호하면 재확인 |
| 관측/추정/권고 분리 | 근거와 추가 확인 사항을 구분 | 생성 모델이 형식·의미를 어길 수 있음 | 구조/수치 검사와 수동 대조를 분리 |
| 코드로 수치/출처 검사 | 재현 가능한 오류 탐지 | 자연어의 모든 주장·원인의 진위를 판단할 수 없음 | 탐지 범위와 통과한 실패 사례 명시 |
| 제한된 재작성 | 오류 수정 기회 | 호출 수·비용·지연 증가 | 한도 후 강제 합격 대신 실패/부분 상태 |
| 생성량·시간 제한 | 장기 대기 제어 | 답변이 잘릴 수 있음, 진행 중 호출 취소 설계 필요 | 중단 이유와 부분 결과 처리 |
| 작은 로컬 모델 | 로컬 반복 개발 가능 | 계획 누락·추론 오류·응답 시간 변동 | 실제 모델 반복 검사, API 결과 별도 보고 |
| 기존 샘플 데이터 활용 | 범위 안에서 검토·반복 가능 | 실제 운영 장애 다양성을 대표하지 않음 | 데모 범위 명시, 일반 정확도 보장 금지 |
| RAG를 후속 후보로 유지 | 핵심 대상/근거 문제에 집중 | 의미 검색과 복합 장애 매뉴얼 선택은 남음 | 핵심 완료 후 별도 검색 평가로 필요성 판단 |

실제 인프라 제어, 승인/권한 체계, 운영 환경 성능 검증은 이번 범위에 포함하지 않는다. 제공 매뉴얼의 조치 제안과 실제 실행된 작업을 구분한다.
