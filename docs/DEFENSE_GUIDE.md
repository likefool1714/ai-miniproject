# 발표·코드 설명 준비

이 문서는 코드 이해를 위한 Markdown 안내다. 최종 PPT·보기용 PDF·5분 대본과 함께 사용한다.
외워서 읽기보다 아래 흐름을 실제 코드와 실행 화면에서 따라가며 설명할 수 있어야 한다.

## 먼저 설명할 프로젝트 한 문장

“제공된 운영 장애 대응 에이전트에 서비스별 조사 이력을 추가하고, 이전·현재 상태를 비교해 복구 여부를 재확인하도록 개선했습니다. 모델의 제안을 수집 근거와 대조하고, 자료가 부족하면 판단을 보류하도록 했습니다.”

실제 운영 서버를 복구하는 제품은 아니다. JSON 샘플과 합성 시나리오로 동작을 검증한 교육용 프로젝트다.

## 수치만 보여 주는 것과 무엇이 다른가요?

“CPU가 높다”를 보여 주는 데서 끝내지 않고 정상 기준과 비교해 무엇을 점검해야 하는지 설명한다.
CPU 89.5%·메모리 55%라면 CPU 쪽 이상을 우선 확인할 근거가 있다고 해석하고, 조회한 CPU 런북에서 반복 호출·배치 중복 등 확인 방향을 연결한다.
하지만 89.5%는 런북의 CPU >90%라는 증설 수치 조건을 충족하지 않으므로 증설보다 원인 점검과 추세 확인을 안내한다.

LLM은 조사 계획·관련 원인 분류·우선 확인할 런북 단계를 선택한다. 코드는 선택의 근거를 검증하고 수치와 조건을 계산한다.
검증된 결과를 자연스러운 상태 설명과 점검 방향으로 구성하는 부분이 `grounding.render_answer`다.
제공 런북의 해설은 미리 검토한 문장이다. 해당 절차 전체가 조회 결과와 일치할 때만 사용한다. 새로운 문서를 자동으로 해설하는 기능까지 구현한 것은 아니다.
복구 재점검은 `recovery.explain_assessment`에서 무엇이 남아 있는지·왜 보류하는지·언제 새 관측이 필요한지 설명한다.

## 두 가지 실행 경로

일반 진단:

```text
대상 확인 → 모델 분류·계획 → 코드 게이트 → MCP 모니터링·런북 조회
→ 관측 저장·복구 판정 → 모델이 근거/런북 항목 선택
→ 코드 검증 → 답변 구성
```

후속 복구 재점검:

```text
이전 대상 복원 → MCP 새 관측 → 저장 → 수치 비교·정책 판정 → 결과
```

후속 재점검의 수치·복구 판정에는 LLM을 호출하지 않는다.
일반 진단의 생성 스키마도 실제 근거 ID·허용 분류·런북 단계 목록으로 좁힌다. 지연 알림만 확인했으면 CPU 원인 분류를 선택 범위에 넣지 않는다.
일반 대화는 별도 경로이며 진단과 같은 근거 검증을 수행하지 않는다.

## 판정 규칙을 실제 숫자로 설명하기

기본 정상 조건은 healthy·CPU <80%·메모리 <85%·활성 알림 0건이다.
최근 유효한 장애 기록이 있고, 이 조건을 만족하는 서로 다른 관측이 최소 5초 간격으로 2회 있어야 복구로 표시한다.
자료 유효시간은 300초다. 값은 [recovery_policy.json](../data/recovery_policy.json)에 있다.

| 관측 | 판정 이유 |
|---|---|
| CPU95 / 메모리90 / degraded / 알림 있음 | 장애 지속 |
| CPU65 / 메모리87 / degraded / 알림 일부 남음 | 개선 방향이지만 아직 정상 조건 미충족 → 부분 회복 |
| CPU55 / 메모리60 / healthy / 알림 없음 | 정상 1회 → 복구 확정 보류, phase는 partial |
| 5초 이상 뒤 새 정상 관측 | 정상 2회 → 복구 확인 |
| 이후 다시 이상 | phase와 별도로 재발 플래그 표시 |
| 조회 실패·미확인·오래된 자료 | 판단 보류(hold) |

“변화 방향이 개선됐다”와 “복구 조건을 충족했다”는 따로 검사한다.
처음 본 서비스가 정상이라는 이유만으로 복구됐다고 말하지 않는다. 이전 장애를 확인하지 못했기 때문이다.
재발은 다섯 번째 phase가 아니라 recovered 이후 이상을 표시하는 추가 플래그다.

조회 실패가 끼면 그 이후의 새 정상 관측부터 다시 2회를 센다.
예전 sample_id 재전송은 정상 횟수를 늘리거나 최근 실패를 해소할 수 없다.
화면·보고서의 현재 판정은 최근 최대 500건을 동일하게 사용한다. 보고서 표는 최근 100건만 보여 준다.
500건 밖의 장애 이력이 사라지면 복구 판정을 보류할 수 있다.

## 교수님 질문에 답하는 근거

**“과거 전후 비교와 최신 재검증은 무엇이 다른가요?”**

10월 20일에는 같은 질문·고정 관측으로 제공 코드와 당시 복구 기능 구현 버전을 비교했다. 조기 복구 확정은 3/3회에서 0/3회, 재발 안내는 0/3회에서 3/3회였다.
첫 수치는 잘못된 확정이므로 줄어야 좋고, 둘째는 필요한 안내이므로 늘어야 좋다.
10월 21일에는 설명 보완 후 개선 코드 전체를 재검증했다. 실제 Ollama 웹 3개 대화에서도 첫 정상 관측의 복구 보류와 재발 안내를 각각 3/3회 확인했으며 다른 기능·예외도 함께 검사했다.
최신 전체 검사에서 원본을 다시 실행한 것은 아니다. 이후 원격 API 검사는 별도의 호환 검사다.
커밋 번호는 코드 상태의 식별자이며, 발표에서는 “제공 코드”, “복구 기능 추가”, “설명 보완”처럼 변경 내용을 먼저 말한다.

**“원본에서 무엇을 바꿨나요?”**

원본은 현재 모니터링과 런북으로 답변했다. 여기에 조사 이력·전후 비교·후속 재점검·연속 정상 확인·재발·보고서를 연결했다.
일반 진단은 자유 문장 초안을 바로 보여 주던 방식에서 근거 ID와 런북 단계 선택을 검증한 뒤 출력하는 방식으로 보완했다.
등록한 개선 5개·추가 5개는 연결된 항목이며, 독립된 알고리즘 10개를 새로 만들었다는 뜻은 아니다.

**“그냥 if문 아닌가요? 모델은 무엇을 하나요?”**

복구의 수치 조건은 규칙으로 구현했다. 같은 측정값에 대한 판정이 모델의 표현에 따라 달라지는 것을 줄이려는 선택이다.
일반 진단의 분류·계획과 원인 후보/런북 항목 선택에는 모델을 사용한다. 모델이 숫자를 새로 쓰거나 조치를 실행했다고 말하게 두지 않는다.
목표는 모델의 지능이나 근본 원인 정답률 향상을 주장하는 것이 아니라, 운영 에이전트의 상태 추적·일관성과 검증 가능성을 높이는 것이다.

**“정상 2회와 5초는 어디서 나온 기준인가요?”**

단발 정상·반복 클릭으로 조기에 복구를 확정하지 않도록 선택한 교육용 정책이다. 산업 표준이나 통계적 신뢰수준으로 주장하지 않는다.
횟수·간격을 늘리면 보수적이지만 확인이 늦어진다. 실제 운영 적용 시 서비스 SLO와 관측 주기로 다시 정해야 한다.
데모의 빠른 재생은 과거 시각을 부여한 합성 관측이므로 실제로 10초마다 서버가 회복한 증거가 아니다.

**“CPU 80%와 런북의 90%는 서로 모순 아닌가요?”**

80%는 이 프로젝트의 정상/복구 정책이다. 런북의 ‘90% 초과 및 지속’은 확장 조치 검토 조건이다.
89.5%는 정상 정책을 벗어나지만 >90% 조건에는 불충족이다. 95%여도 지속 시간·배포·트래픽을 읽지 않았으므로 확장을 실행했다고 말하지 않는다.

**“근거 검증이면 모든 답이 맞다는 뜻인가요?”**

확보한 관측의 값·시각·대상과 모델이 선택한 ID·분류·런북 단계의 일관성을 검사한다.
실제 장애 원인·런북 자체의 정확성·관측 사이의 상태·일반 대화의 모든 사실까지 검증하지 않는다.
표현과 후보 범위를 제한해 안정성을 얻는 대신 자유로운 설명 능력은 줄었다.
검증 실패 시 재작성은 한 번이며 다시 실패하면 보류한다. 오류 답변을 강제 통과시키지 않는다.

**“RAG와 LLM-as-a-Judge도 구현했나요?”**

현재는 증상 규칙으로 incident_type을 고르고 MCP Resource의 정적 런북을 읽는다. 벡터 검색 RAG를 추가 구현했다고 하지 않는다.
Validator는 코드 검사다. 다른 LLM이 응답을 채점하는 LLM-as-a-Judge 구현으로 설명하지 않는다.
자료 p.11~12는 개선 예시이며, p.10은 기능 개선에 제약이 없다고 설명한다. 적용한 기술과 제외한 기술을 구분해서 말한다.

**“왜 SQLite이고 LangGraph Checkpointer는 아닌가요?”**

짧은 기간의 로컬 프로젝트에서 별도 DB 서버 없이 대상·관측·실패를 유지하기 위해 SQLite를 사용했다.
내장 Checkpointer를 도입한 것이 아니라 상태 저장·복원 목적을 별도 저장소로 구현했다.
다중 서버 운영, 사용자 인증, 장기 보관·삭제 정책은 범위 밖이다.

**“전후 속도 차이는 LLM을 안 불러서 그런 것 아닌가요?”**

후속 복구 경로가 모델을 생략하기 때문에 빨라진 효과가 포함된다. 그 점을 결과에 명시했다.
모델 추론 자체를 동일 조건에서 가속했다거나 검색 정확도를 높였다는 뜻은 아니다.
작성 단계 비교·고정 MCP fixture 비교·실제 HTTP 시간을 구분한다. 로컬 cost_usd는 가상 단가이며 실제 API 청구액이 아니다.
원본 research의 0.35초 데모 지연과 MCP의 최초 1회 모의 timeout도 남아 있으므로 실제 운영 네트워크 지연이라고 설명하지 않는다.

**“테스트가 데모 정답을 정해 놓고 맞춘 것 아닌가요?”**

합성 데모는 정책을 재현하는 용도다. 이것만으로 실제 장애 정답률을 주장하지 않는다.
경계값·392개 조건 조합·조회 실패·중복/충돌·자료 만료·재시작·100/500건 경계도 별도로 검사했다.
기존 48개 검사가 통과해도 새 경계 검사에서 오류 세 가지가 발견돼 수정했다. 검사 수가 무오류 보증이 아니라는 한계도 공개한다.

**“제공 코드를 얼마나 재사용했고, 남은 것은 무엇인가요?”**

제공 Supervisor, MCP Tool/Resource/Prompt, 모델 백엔드, Vue/SSE, 의존성 주입 구조를 재사용했다.
추가 핵심은 recovery.py, recovery_store.py, recovery_nodes.py, grounding.py와 연결·검사 코드다.
기존 선택적 analysis 노드의 자유 문장 결과는 현재 Writer의 일차 근거로 쓰지 않는다. 불필요한 호출 제거는 추가 최적화 여지가 있다.
제공 API 실제 진단 POST 3건·SSE 1건, 복구 5단계·이력·보고서를 확인하고 최종 PPT/PDF·대본을 작성했다. LangSmith는 미검증이며 실제 발표·최종 제출은 별도다. [API 증거](../results/api-2026-10-21/README.md)를 확인한다.

## 2분 설명 연습 순서

1. 프로젝트 한 문장을 말한다.
2. 위의 숫자 예시로 정상 1회와 정상 2회의 차이를 말한다.
3. request_context → collect → store → assess → answer를 코드에서 짚는다.
