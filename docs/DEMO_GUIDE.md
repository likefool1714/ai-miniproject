# 발표 전 직접 확인하기

## 1. 현재 앱 열기

http://127.0.0.1:8600/ 에 접속하고 새로고침합니다. 왼쪽의 **새 조사 시작**을 누릅니다.
상단 **에이전트 연결됨**을 확인하고 왼쪽 아래 **실행 환경**을 펼칩니다. 현재 모델 백엔드는 openai입니다.
모델명 표시나 연결 상태만으로 실제 API 호출 성공을 증명하지는 않습니다. 실제 호출은 아래 일반 진단과 [10/22 검증 요약](../results/api-2026-10-22/README.md)으로 확인합니다.

## 2. 실제 API 진단 → 복구 5단계

다음 질문을 그대로 입력합니다.

> payments-service 장애를 진단해주세요

같은 대화에서 왼쪽 **복구 재점검**을 네 번 누릅니다. 각 답변이 끝난 뒤 다음 버튼을 누릅니다.

| 순서 | 확인할 값·내용 | 기대 결과 |
|---|---|---|
| 최초 일반 진단 | CPU 95%, 메모리 90%, 알림 2건 | 장애 지속, 근거와 점검 방향 설명 |
| 재점검 1회 | CPU 65%, 메모리 87%, 알림 1건 | 부분 회복, 아직 메모리·알림 문제 |
| 재점검 2회 | CPU 55%, 메모리 60%, 알림 0건 | 정상 1/2회, 복구 확정 보류 |
| 재점검 3회 | CPU 54%, 메모리 58%, 알림 0건 | 정상 2회, 정책상 복구 확인 |
| 재점검 4회 | CPU 94%, 메모리 60%, 알림 1건 | 장애 재발 / 장애 지속 |

정상 2회·최소 5초는 합성 관측 시각에 적용하는 교육용 정책입니다. 버튼을 실제로 5초마다 누를 필요는 없습니다.
일반 진단의 분류·계획·런북 선택에 원격 모델을 사용하고, 후속 복구 판정에는 모델을 호출하지 않습니다.
기본 시나리오는 다섯 번째 단계에서 멈춥니다. 이후 계속 누르면 같은 마지막 관측이므로 정상 횟수가 새로 늘지 않습니다.

## 3. 이력과 보고서

- **조사 이력**: 같은 서비스의 위 관측 5건과 당시 판정을 확인합니다.
- **보고서 내보내기**: 현재 판정·변화·이력·정책·한계를 확인하고, 답변 아래 `.md` 다운로드 링크를 누릅니다.
- 이력·보고서는 저장 기록을 읽습니다. 이 버튼을 눌렀다고 관측이 6건·7건으로 증가하면 안 됩니다.
- 보고서는 메모장/코드 편집기 등에서 열 수 있는 Markdown 텍스트 파일입니다.

5분 이상 지난 관측은 현재 상태의 근거로 쓰기 어려워 **판단 보류**가 나올 수 있습니다. 정상적인 유효기간 검사입니다. 새 조사를 시작하고 처음부터 재현하세요.
페이지 새로고침은 화면 대화를 지워도 서버의 같은 대화 이력은 남을 수 있습니다. 시나리오를 초기화하려면 반드시 **새 조사 시작**을 누릅니다.

## 4. 대상 확인 기능

새 조사에서 `복구됐어?`를 보내면 어떤 서비스인지 질문해야 합니다.
`결제 서비스 상태요`라고 답하면 기다리던 재점검을 이어갑니다.
`결제 서비스 말고 인증 서비스만 다시 확인해 주세요`에서는 인증 서비스만 조사해야 합니다.
두 서비스를 조사한 뒤 `그 서비스`라고만 하면 모호하므로 대상을 다시 질문합니다.

## 5. 발표에서 구분할 것

- 과거 10/20 수치: 같은 5단계 입력을 세 번 반복한 전후 비교입니다.
- 성급한 복구 확정: 3회 → 0회. 재발 안내 누락: 3회 → 0회입니다. 둘 다 오류가 줄었다는 뜻입니다.
- 10/22 원본 사진은 원본 그래프+실제 Ollama를 현재 Vue에 연결한 실행입니다. 개선 사진은 코드 기반 복구 재점검입니다.
- 새 사진과 과거 3회 비교를 합산하지 않습니다. 모델 추론 속도나 일반 정확도가 개선됐다고 확대하지 않습니다.
- 앞선 API 검사는 POST 3건·SSE 1건/원격12호출입니다. 이번 수정본 검사는 POST 4건/원격14호출이며 별도 실행입니다. 진단 건수와 내부 모델 호출 수는 다른 집계 단위입니다.
- 실제 서버 조치·결제 성공 확인은 구현하지 않았고, 모니터링은 합성 데이터입니다.

현재 코드에서 읽을 순서는 request_context_node → recovery_collect_node → RecoveryStore.record → assess → render_assessment입니다.
일반 진단에서는 추가로 grounding.validate_draft가 모델의 근거·런북 선택을 검사합니다.

## 외부 검토 반영 후 주의점
새 시나리오 단계는 조회 시점 기준으로 생성하므로 90초 간격5단계도 새 자료로 판정한다. 마지막 동일 관측의 ID·시각은 바꾸지 않으므로 5분 뒤 계속 읽으면 보류하는 보호는 유지한다. 과거 장애는3600초 범위로 현재 자료의300초와 구분한다.
복구 방법·원인 분석은 일반 진단, 복구됐어는 재점검, 보고서 형식은 진단 경로, 보고서 내보내기는 파일 생성이다. [수정 검증](../results/review-fixes-2026-10-22/README.md).
