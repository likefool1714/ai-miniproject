# 제공 API 실제 연결 확인

2026-10-21 기준 준비 절차다. 아직 실제 제공 API를 호출해 통과한 결과가 아니다.
현재 프로젝트 루트에는 `.env`가 없다. 키 값은 문서·채팅·검증 결과에 적지 않는다.

## 무엇이 바뀌는가

브라우저(8600) → 백엔드(8100) → 모델 API로 연결된다. 기존 MCP 모니터링·런북, SQLite 이력, 복구 정책은 그대로 사용한다.
Ollama 대신 분류·계획·진단 항목 선택을 원격 모델에 요청한다. API로 바꾸어도 모니터링은 합성 시나리오이며 실제 운영 서버 데이터가 되지는 않는다.

현재 `agent/openai_llm.py`의 접속 주소는 `https://api.openai.com/v1/chat/completions`로 고정되어 있다.
교육기관이 별도 프록시 주소나 다른 인증 방식을 제공했다면 키만 넣어서는 연결되지 않으므로 안내 주소·요청 형식을 먼저 대조해야 한다.
기본 모델은 `gpt-4o-mini` / `gpt-4o`이며 사용 가능 여부는 제공받은 계정·모델 권한으로 확인한다. `.env`의 `OPENAI_FAST_MODEL` / `OPENAI_QUALITY_MODEL`로 수업에서 허용한 모델을 지정할 수 있다.

## 1. 실행 전 준비

프로젝트 루트에서 진행한다. 기존 서버가 켜져 있다면 해당 터미널의 Ctrl+C로 종료한 뒤 8100 포트를 사용한다.

```bash
# 기존 .env가 있으면 덮어쓰지 않는다.
[ -f .env ] || cp .env.example .env
```

로컬 편집기로 `.env`의 `OPENAI_API_KEY`에 제공받은 실제 키를 입력한다.
키는 서버에서 읽으며 브라우저에 입력하지 않는다. `.env`는 Git 제외 대상이다.
추적을 별도로 확인하기 전에는 다음 설정을 사용한다.

```dotenv
LANGCHAIN_TRACING_V2=false
LANGSMITH_TRACING=false
```

LangSmith는 별도 추적 서비스이므로 모델 API 연결과 나누어 검사한다. 이후 추적이 필요하면 별도의 유효 키·프로젝트를 설정하고 실제 실행 기록 생성까지 확인한다.

## 2. API 백엔드와 웹 실행

과제에서 안내한 실행 방식은 다음과 같다. 스크립트의 실제 호출 안내를 읽고 계속 진행한다.

```bash
MONITORING_SCENARIO=recovery-demo SESSION_DB_PATH=api-verification.db \
bash sh/run_agent_openai.sh
```

이 스크립트는 기존 8100 포트 프로세스를 종료하므로 실행 전 기존 백엔드를 정상 종료한다.
스크립트는 `.env`를 읽고 `LLM_BACKEND=openai`, `SUPERVISOR_VERSION=v2`로 기동한다. 서버 기동만으로 모델 호출 성공이 증명되지는 않는다.

별도 터미널에서 웹이 꺼져 있을 때만 실행한다.

```bash
.venv/bin/python -m uvicorn web_demo_server:app --host 127.0.0.1 --port 8600
```

- 상태: http://127.0.0.1:8100/health
- 화면: http://127.0.0.1:8600/
- 상태 응답에서 `llm_backend=openai`, `supervisor_version=v2`, `monitoring_mode=recovery-demo` 확인.

## 3. 실제 모델 호출 확인

**복구 재점검·이력·보고서는 모델을 호출하지 않는다. 이것만 검사하면 API 테스트가 아니다.**

1. 화면에서 **새 조사**를 누르고 `payments-service 장애를 진단해주세요`를 보낸다.
2. 응답 성공뿐 아니라 `/health`의 모델 이름, 진단 응답의 `metadata.validation_status=validated` 여부, CPU 95%·메모리 90%·출처와 설명을 확인한다. 모델 선택 결과가 반려되어 안전한 대체 답변을 반환했다면 검증 통과와 구분해 기록한다. 검증 통과는 제한된 출력 계약에 대한 판정이며 모든 진단의 정확성 보장은 아니다.
3. 같은 대화에서 `그 서비스 복구됐어? 다시 확인해줘`를 네 번 보낸다.
4. `장애 지속 → 부분 회복 → 부분 회복(정상 1회) → 복구 확인 → 장애 재발`을 확인한다. 마지막 항목은 내부 상태 `ongoing`에 `recurrence=true`가 붙는 방식이다.
5. **조사 이력**에서 관측 5건과 대상 유지, **Markdown 보고서**에서 다운로드·재발 내용·출처를 확인한다. 이 두 조회로 관측 수가 늘지 않아야 한다.
6. 추가로 새 대화에서 대상 없는 진단의 확인 질문, 복수 서비스 진단, 정상 서비스 진단을 확인한다.

기본 단일 시나리오 확인은 제한된 연결 검사다. 실패·변동이 있으면 해당 사례를 보존하고 원인을 확인한 뒤 필요한 범위를 재검사한다.
시나리오 관측 시각은 합성 데이터로 10초 간격이다. 실제 운영 서버를 그 간격으로 측정했다는 의미가 아니다. 300초 넘긴 자료는 보류할 수 있으므로 오래 걸렸다면 **새 조사**로 시작한다.

## 4. 남길 증거와 완료 기준

- 실행 날짜·코드 커밋·모델명·질문·같은 대화 ID·응답 원문·검증 상태·지연시간.
- 최초 일반 진단과 후속 복구 단계, 이력·보고서 화면. 키와 인증 헤더를 포함하지 않는다.
- API 응답의 토큰 사용량과 화면의 가상 단가 추정치를 구분한다. 현재 채팅 응답 metadata에는 토큰 수를 보존하지 않으므로, 토큰 비교가 필요하면 별도 검증 기록이나 실제 추적에서 확인 가능한 사용량을 수집한다. 미수집 값은 적지 않는다. `cost_usd`는 실제 청구액이 아니다.
- 인증/모델 권한/한도/네트워크 오류가 발생하면 API 검증을 완료로 표시하지 않는다.
- 위 결과를 확인한 뒤 README의 API 미검증 상태를 실제 결과로 갱신한다. Ollama 측정값을 API 결과로 옮겨 적지 않는다.

확인 순서: **실제 진단 API 호출 → 후속 기능 확인 → 필요한 추적 확인 → 결과 정리 → 최종 PPT·대본 작성**.
새 기능 후보를 추가로 구현하지 않아도 처음 등록한 범위의 마무리는 진행할 수 있다.

공식 참고: [서버 환경에서 API 키를 읽고 인증하는 방법](https://developers.openai.com/api/reference/overview).
