# 5분 발표 대본

2026-10-21 작성. 내일 발표를 위한 내용 초안이며, 최종 PPT 파일은 API 실제 검사 결과를 확인한 뒤 확정한다.
등록 기능은 로컬 구현·검증 완료다. API·LangSmith 결과는 미검증 상태이며 성공했다고 읽지 않는다.
시간은 목표치다. 실제로 읽어 녹음한 시간이 아니므로 내일 두 차례 연습해 조정한다.

## 1장. 정상 수치 한 번으로 복구를 확정하는 문제 — 40초

안녕하세요. 과제 1번으로 운영 장애 대응 에이전트의 상태 비교와 복구 확인 기능을 개선한 G028 최민석입니다.
제공된 에이전트는 모니터링 수치를 조회하고 런북을 참고해 대응 방법을 설명합니다.
하지만 현재 수치가 정상이라는 것과 장애가 안정적으로 회복됐다는 것은 구분할 필요가 있었습니다.
고정 시나리오에서 원본은 정상 관측 한 번만으로 복구를 확정했습니다.
그래서 이전 조사 기록과 연속 관측을 사용해 복구 판단의 근거를 남기도록 개선했습니다.

화면: 정상 1회에서 원본과 개선 응답 비교. 출처: `results/recovery-2026-10-20/`, `results/qa-comparison-2026-10-21/`.

## 2장. 모니터링 조회에서 판단·설명까지의 흐름 — 40초

사용자가 결제 서비스 장애를 질문하면 먼저 조사 대상을 확인합니다.
기존 MCP Tool로 모니터링을 조회하고 Resource로 대응 매뉴얼인 런북을 읽습니다.
제가 추가한 저장소는 대화와 서비스별로 관측을 기록합니다.
이전 관측과 비교한 뒤 코드가 복구 정책을 계산합니다.
LLM은 조사 계획과 원인 후보·런북 항목 선택에 사용합니다.
선택한 내용이 실제 근거와 맞는지는 코드가 검사하고, 검증한 수치와 점검 방향을 답변으로 구성합니다.

화면: 기존 구성과 추가 모듈을 나눈 처리 순서. 핵심 파일: `recovery_nodes.py`, `recovery_store.py`, `recovery.py`, `grounding.py`.

## 3장. 이전 상태와 연속 관측으로 복구 판단 — 70초

이 예시는 실제 운영 서버가 아닌 합성 모니터링 시나리오입니다.
첫 관측은 CPU 95%, 메모리 90%로 장애가 지속됩니다.
다음 관측에서 CPU가 65%로 떨어져도 메모리는 87%이고 알림이 남아 있어 부분 회복입니다.
그다음 CPU 55%, 메모리 60%로 정상 조건을 만족하더라도 정상 관측이 한 번뿐이라 복구를 확정하지 않습니다.
최소 5초 이상 떨어진 새 관측에서도 정상 조건을 만족하면 정상 두 번으로 복구를 확인합니다.
같은 관측을 반복 조회하는 것은 정상 횟수에 포함하지 않습니다.
자료가 오래됐거나 조회에 실패한 경우에도 판단을 보류합니다.
또 숫자만 나열하지 않도록, 남아 있는 문제와 추가로 확인할 조건을 설명했습니다.

화면: 실제 앱의 정상 1회 보류 응답과 다음 정상 관측. 출처: `results/explanation-2026-10-21/app-recheck.jpg`, 최신 실행 원문 `results/status-2026-10-21/live-check.json`.

## 4장. 재점검·재발·이력·보고서 — 40초

후속 질문에서 “그 서비스 다시 확인해줘”라고 하면 같은 대화의 조사 대상을 이어받아 새 모니터링을 조회합니다.
복구 이후 다시 이상이 관측되면 재발로 표시합니다. 같은 원인이 재발했다고 단정하지는 않습니다.
사용자는 조사 이력과 수치 변화·알림 해소 내역을 조회하고 Markdown 보고서로 저장할 수 있습니다.
이력과 보고서 열람은 새로운 모니터링을 실행하지 않습니다.
기존 대화 메시지 저장은 재사용했고, 서비스 관측·판정·조회 실패 기록을 추가했습니다.

화면: 새 데이터 조회와 저장 기록 열람의 구분, 이력 및 보고서 실제 화면.

## 5장. 같은 관측을 사용한 개선 전후 비교 — 70초

비교에서는 같은 질문과 다섯 단계 관측을 원본과 개선 코드에 넣고 세 번 반복했습니다.
정상 한 번으로 조기 복구를 확정한 경우는 원본 세 번에서 개선 후 영 번으로 줄었습니다.
복구 후 재발을 명시한 경우는 영 번에서 세 번으로 늘었습니다.
이는 제한된 고정 시나리오의 결과이며 전체 장애 진단 정확도는 아닙니다.
이후 실제 로컬 웹·MCP·Ollama 경로에서도 세 주기의 열다섯 상태 판정이 기대 결과와 일치했습니다.
추가로 자동 검사 67개와 정상 조건 조합 392개를 확인했습니다. 자동 검사의 모델은 모의 객체이며 실제 LLM 실행과 구분했습니다.
후속 복구 판정은 LLM을 호출하지 않으므로 빠르지만, 이를 모델 추론 자체의 속도 개선이라고 설명하지 않습니다.

화면: 조기 복구 3/3 대 0/3, 재발 명시 0/3 대 3/3의 비교 표. 검사 수는 작은 보조 문구로 표시.
출처: `results/recovery-2026-10-20/`, `results/revalidation-2026-10-21/README.md`.
API 결과는 실제 확인 후 별도로 반영한다. Ollama 결과를 API 결과로 바꿔 적지 않는다.

## 6장. 정책 의존성과 실제 운영 적용의 한계 — 40초

정상 두 번과 관측 간격을 요구하면 일시적 정상화에 신중해지는 대신 복구 확인이 늦어집니다.
임계값과 횟수는 교육용 정책이므로 실제 적용 시 서비스별 기준으로 조정해야 합니다.
합성 데이터로 기능을 검증했기 때문에 실제 결제 성공이나 근본 원인 제거를 증명하지는 않습니다.
근거 검증 역시 확보한 자료와 답변의 일관성을 검사하는 범위입니다.
추후 실제 지표와 서비스별 기준을 연결하고, 필요한 경우 관련 서비스 조사나 변경 이력을 확장할 수 있습니다.
이 후보들은 현재 구현 기능과 구분했습니다. 감사합니다.

## API 결과 반영 위치

- API 실제 검사 전: “로컬 검증 완료, 제공 API 연결 미검증”으로 표기한다.
- 실제 검사 후: 검사 날짜·모델·검증 상태·확인한 범위를 근거 파일과 함께 기록한다.
- 실패/대체 응답/부분 성공은 그대로 기록한다. 성공으로 바꿔 읽지 않는다.
- LangSmith도 실제 실행 기록을 확인한 경우에만 완료로 설명한다.

## 발표 직전 기억할 답변 네 가지

1. 왜 규칙으로 판단하나요? 같은 수치에 대한 복구 판단을 일정하게 유지하려는 선택입니다. LLM은 계획과 진단 항목 선택에 사용합니다.
2. 정상 2회는 표준인가요? 교육용 정책입니다. 횟수를 늘리면 신중해지지만 확인이 늦어집니다.
3. MCP를 새로 만들었나요? 제공 MCP 연결과 기능을 재사용하고 새 관측·이력·판정 흐름을 연결했습니다.
4. 전부 정확한가요? 제한된 관측과 런북의 일관성을 확인합니다. 근본 원인과 모든 자연어 사실을 보장하지 않습니다.
