# 실제 화면 비교에 맞춘 5분 발표 대본

표지 포함 9장, 목표 300초. 화면에는 핵심과 실제 증거를 두고 설명은 말로 전달한다.
이름은 표지 좌측 하단에만 작게 표기한다.

## 1. 표지 - 15초

안녕하세요. G028 최민석입니다. 과제 1번으로 제공된 운영 장애 대응 에이전트를 개선했습니다.
상태 변화 추적과 근거 기반 복구 확인을 중심으로, 왜 개선했는지와 실제 질문에서 무엇이 달라졌는지 말씀드리겠습니다.

## 2. 기존 구조 - 25초

기존 코드는 질문을 받으면 모델이 계획을 세우고, MCP로 모니터링과 런북을 조회한 뒤 답변했습니다.
MCP는 이 도구와 문서를 표준 방식으로 연결하는 역할이며 기존 제공 구성을 재사용했습니다.
그런데 기존 검사는 답변 길이와 번호 형식이 중심이었습니다. 화면의 한 줄이 그 검사입니다.
답변이 길고 형식이 맞아도 실제 조사 근거와 내용이 맞는지는 별도로 확인할 필요가 있었습니다.

## 3. 추가한 처리 - 25초

복구됐는지 설명하려면 지금 수치뿐 아니라 이전 관측이 필요하다고 판단했습니다.
그래서 서비스 관측을 SQLite에 저장하고, 이전 수치와 알림을 비교하는 처리를 추가했습니다.
모델은 일반 진단의 계획과 항목 선택에 사용하고, 수치 비교와 복구 판정은 코드 정책으로 처리했습니다.
일반 진단의 모델 제안도 실제 관측 ID와 런북 항목에 맞는지 검사합니다.

## 4. 개선 전 실제 답변 - 40초

이번에는 그림으로 답변을 만들어 놓은 것이 아니라, 제공 원본을 실행한 채팅 화면입니다.
같은 결제 서비스에 장애 관측 다음 정상 첫 관측을 넣었습니다. CPU 55%, 메모리 60%, 알림 0건입니다.
원본은 서비스 복구 완료라고 판단했습니다.
또 실제로 수집한 것은 모니터링과 런북인데, 별도 커넥션 풀이나 리플리케이션 점검까지 수행한 것처럼 답했습니다.
그래서 정상 한 번과 안정적인 복구를 구분하고, 실제 확보한 근거 안에서 설명하도록 개선했습니다.

발표자 참고: d1043ff 원본 그래프·원본 Ollama 어댑터의 실제 생성이다. 모니터링은 고정 합성 입력이고 이번 사진은 단일 사례다. 실제 DB 점검이나 실제 서비스 복구를 재현한 것이 아니다.

## 5. 개선 후 실제 답변 - 35초

수정본에 같은 관측값과 장애 다음 정상이라는 순서를 넣었습니다.
이번에는 정상 관측이 1/2회이므로 복구 확정은 보류한다고 답했습니다.
수치만 나열하지 않고 일시적인 정상화일 수 있다는 이유와, 최소 5초 간격의 새 정상 관측이 더 필요하다는 조건을 설명했습니다.
CPU와 메모리가 얼마나 내려갔고 어떤 알림이 해소됐는지도 근거로 보여줍니다.
정상 두 번과 5초 간격은 이번 교육용 정책이며 실제 운영 표준을 뜻하지 않습니다.

발표자 참고: 복구 재점검은 모델 생성 없이 코드가 판단·설명하는 경로다. 원본과 추론 속도가 개선됐다는 비교는 하지 않는다. 합성 관측 시각 간격을 사용했으며 실제 5초마다 정상 서비스가 지속됐다는 증거가 아니다.

## 6. 판정과 근거 검증 - 45초

왼쪽은 유효한 정상 관측을 세는 코드입니다. 전체 함수에서는 수치·상태·알림과 중복·시각 조건을 함께 봅니다.
추가 감사에서는 전체 요청 시간 초과가 연속성 기록에 빠지는 문제도 찾아, 실제 수집이 취소되면 실패 경계를 남기도록 고쳤습니다.
가운데는 모델의 제안을 근거 검증 함수로 넘기는 부분입니다. 없는 근거나 다른 서비스의 런북 항목은 채택하지 않습니다.
오른쪽 strict 옵션은 true나 false가 1%, 0%로 바뀌어 정상 판정에 쓰이는 것을 막습니다.
이렇게 모델이 제안하는 부분과 코드가 확인할 수 있는 부분을 나눴습니다.

발표자 참고: 실제 코드의 별도 위치 발췌이며 한 함수 전체가 아니다. validate_draft 구현은 grounding.py, 취소 처리는 recovery_nodes.py/graph.py, strict 필드는 recovery.py와 mcp_server.py에 있다. 모든 자유 대화의 사실성을 보장하는 검증이 아니다.

## 7. 개선 전후 - 50초

여기는 앞의 단일 캡처와 별개로, 10월 20일 같은 다섯 단계 관측을 세 번 반복한 결과입니다.
정상 한 번으로 잘못 복구를 확정한 횟수는 3회에서 0회로 줄었습니다.
필요한 재발 안내는 반대로 0회에서 3회로 늘었습니다. 오류와 필요한 안내라 숫자가 좋아지는 방향이 다릅니다.
오늘 추가 감사에서 찾은 네 종류의 버그를 고친 뒤에는 기존 검사와 새 회귀 검사 총 77개를 통과했습니다.
제공 API에서도 일반 진단 POST 세 건, SSE 한 건과 복구·이력·보고서가 작동하는지 다시 확인했습니다.
고정 시나리오의 결과와 호환 검사이므로 전체 장애 진단 정확도라고 확대하지 않았습니다.

발표자 참고: 10/20 5단계×3회와 10/21 화면의 4관측, 별도 제공 API 5단계는 서로 다른 실행이다. 신규 검증을 과거 원본 비교의 추가 반복으로 합산하지 않는다.

## 8. 조사 이력과 보고서 - 40초

한 번의 답변만 남으면 다음 질문에서 이전 상태를 비교하거나 복구 이후 다시 나빠졌는지 설명하기 어렵습니다.
그래서 조사 이력 저장·조회, 수치와 알림 변화 비교, 새 관측을 가져오는 재점검, 복구 이후 재발 안내, Markdown 보고서를 추가했습니다.
이 화면은 실제 이력 버튼을 눌러 장애, 부분 회복, 복구 확인, 재발 네 건을 조회한 결과입니다.
이력과 보고서는 저장 자료를 읽고, 재점검은 새 자료를 조회합니다.
기록은 같은 대화의 서비스별로 분리하며, 보고서로 관측 근거와 판정 조건을 전달할 수 있습니다.

발표자 참고: 비교·저장·판정을 여러 기능이 공유하므로 독립 알고리즘 10개라고 설명하지 않는다. 스크린샷의 파일 다운로드 링크 생성과 실제 HTTP 다운로드 검증 기록은 구분한다.

## 9. 한계와 다음 단계 - 25초

합성 모니터링으로 검증했으므로 실제 사용자 결제 성공이나 근본 원인 제거까지 확인하지는 않았습니다.
연속 정상 관측을 요구하면 성급한 확정은 줄지만 복구 확인이 늦어집니다.
코드 정책은 일관성이 있지만 진단 범위와 자연어 해석에 제한이 있습니다.
실제 지표와 서비스별 기준 연결이 다음 단계이며, LangSmith 실제 추적과 배포 이력 연계는 확인한 기능으로 포함하지 않았습니다. 감사합니다.

## 질문 대비

- MCP를 새로 구현했나요? 제공 MCP 연결·Tool·Resource·Prompt 구성을 재사용하고 관측 이력·복구 정책·근거 검증을 연결했습니다.
- 모델은 무엇을 하나요? 일반 진단의 분류·계획·진단 항목과 런북 절차 선택에 사용합니다. 복구 재점검·이력·보고서는 코드 경로입니다.
- 왜 복구를 규칙으로 판단하나요? 같은 수치를 두고 답변마다 복구 여부가 달라지는 것을 줄이려는 선택입니다. 정책은 실제 운영 시 SLO·관측 주기에 맞게 정해야 합니다.
- 시간 초과는 어떻게 고쳤나요? 수집 중 CancelledError에서 실패 경계를 저장하고 취소를 전파합니다. 단순 잠금 대기는 기존 정상 관측을 무효화하지 않습니다.
- 원본도 오늘 전체 다시 검사했나요? 원본의 오늘 사진은 고정 관측 단일 실행입니다. 과거 3회 비교·오늘 77개 회귀 검사·실제 API 검사는 별개입니다.
- 제외 표현을 전부 이해하나요? 명확한 말고·제외·빼고 표현과 짧은 대상 선택 답변을 처리합니다. 모든 자연어를 완전하게 해석한다는 주장은 하지 않습니다.
