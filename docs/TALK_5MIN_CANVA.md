# 최종 5분 발표 대본 — 본문 10장

본문 목표 합계 300초. 부록 11~13장은 질문 시 사용한다. 연습 시 실제 시간을 측정한다.

## 1. 표지 — 15초
안녕하세요. G028 최민석입니다. 제공된 운영 장애 대응 에이전트에 상태 변화 비교와 근거 기반 복구 확인을 추가했습니다. 기존 문제와 실제 답변이 어떻게 달라졌는지 설명드리겠습니다.

## 2. 기존 구조 — 20초
기존에는 모델이 계획을 세우고 MCP로 모니터링과 런북을 조회해 답변했습니다. MCP는 도구와 문서를 연결하는 통로입니다. 기존 검사는 길이와 번호 형식 중심이어서, 내용이 실제 근거와 일치하는지 보완할 필요가 있었습니다.

## 3. 개선 전 실제 답변 — 35초
원본 그래프를 실제 Ollama로 실행하고 현재 Vue로 촬영했습니다. 장애와 부분 회복 다음 CPU55%, 메모리60%, 알림0건이 처음 나오자 복구 완료라고 답했습니다. 조회하지 않은 커넥션 풀·리플리케이션 점검도 수행했다고 표현했습니다. 따라서 정상 한 번과 복구를 구분하고, 확보한 근거 안에서 설명하도록 개선했습니다.

## 4. 추가한 처리 — 20초
이전 관측이 있어야 상태 변화를 설명할 수 있어 SQLite 이력을 추가했습니다. 요청 대상을 확인하고 새 관측을 저장한 뒤 변화와 복구를 판단합니다. 일반 진단의 모델 제안은 근거 검사를 거쳐 표시합니다.

## 5. 판정과 근거 검증 — 35초
왼쪽은 정상 관측 집계입니다. 수치·상태·알림과 시간·중복·조회 실패를 함께 봅니다. 현재 자료의 300초 유효기간과 과거 장애의 3600초 범위도 분리했습니다. 가운데는 근거 ID와 런북 항목 검증이고, 오른쪽 strict는 true·false가 백분율로 들어오는 것을 막습니다.

## 6. 기술 요소와 설계 선택 — 30초
LangGraph와 MCP는 제공 구조를 재사용하고 분기와 관측 문맥을 확장했습니다. RecoveryStore를 주입하고 새 모듈 다섯 개로 책임을 나눴습니다. 기존 역할 분담과 런북 조회를 유지하며 새 벡터 검색·자율 협업은 추가하지 않았습니다. 이번에는 호출과 검증 범위를 제한하고 판정·근거 검사를 우선했습니다. 두 기술의 성능 우위는 비교하지 않았습니다.

## 7. 개선 후 실제 답변 — 30초
같은 첫 정상 관측에서 개선본은 정상1/2회이므로 복구 확정을 보류합니다. 수치만 나열하지 않고 일시적 정상화 가능성과 다음 정상 관측 조건을 설명합니다. 정상2회·최소5초는 교육용 정책이고, 복구 재점검의 판단과 설명은 모델 생성 없이 코드가 처리합니다.

## 8. 개선 전후 — 45초
위 표는 10월20일 동일한 합성5단계를 세 번 반복한 기록입니다. 성급한 복구 확정과 재발 안내 누락 모두 오류3회에서0회로 줄었습니다. 아래는 별도 최신 검증입니다. 시간 경과와 오분류 수정을 포함해91개 검사를 통과했습니다. 실제 API 진단4건도 검증을 통과했고 내부 원격호출14건이 HTTP200이었습니다. 전체 장애 진단 정확도로 확대하지 않았습니다.

## 9. 추가한 기능 — 40초
이전 답변만으로는 다음 조사와 비교하거나 재발을 설명하기 어렵습니다. 그래서 이력 저장·조회, 변화 비교, 새 관측 재점검, 복구 이후 재발 감지, Markdown 보고서를 추가했습니다. 화면은 실제 관측5건입니다. 이력·보고서는 저장 자료를 읽고 재점검만 새 자료를 가져옵니다. 여러 기능이 저장·판정 코드를 공유합니다.

## 10. 한계와 다음 단계 — 30초
합성 모니터링이므로 실제 결제 성공이나 근본 원인 제거는 확인하지 않았습니다. 신중한 판정은 복구 확인을 늦추며, 의도 분기를 보완했어도 모든 자연어를 검증하지는 않았습니다. 실제 지표와 서비스별 기준 연결이 다음 단계입니다. 관련 서비스·배포 이력과 LangSmith 실제 추적은 확인한 기능에 포함하지 않았습니다. 감사합니다.

## 질문 대비 — 본문에서는 읽지 않음
- 왜 RAG를 안 썼나요? 런북 Resource 조회는 사용했습니다. 제공 문서 범위에서 새 벡터 검색 구축 대신 상태 이력과 복구 판정 개선을 선택했습니다.
- Multi-Agent가 없나요? 기존 조사·분석·작성 역할 분담을 재사용했습니다. 독립 에이전트 토론 같은 새 협업은 추가하지 않았습니다.
- 그럼 할루시네이션은 없나요? 제거를 보장하지 않습니다. 모델의 구조화 제안과 실제 근거를 대조하고, 원인 후보·미수집 자료·미실행 조치를 구분합니다.
- 최종 문장도 모델이 쓰나요? 일반 진단에서 모델은 분류·계획·선택적 분석·근거/항목 선택을 합니다. 최종 설명은 검증된 항목과 관측·런북을 코드가 연결해 구성합니다.
- 5분 뒤에는 무조건 보류인가요? 현재 관측이 오래됐으면 보류합니다. 새 관측이 계속 있으면 과거 장애를3600초 범위에서 유지하므로 처음 장애가5분 지났다는 이유만으로 뒤집히지 않습니다.
- 느린 시연은요? 새 단계는 조회 시점 기준 시각으로 생성합니다. 마지막 같은 관측은 시각을 갱신하지 않아 오래되면 보류합니다.
- 로그도 분석하나요? 실제 로그 도구는 없습니다. 요청을 진단으로 분류해도 실제 수집한 것은 모니터링·런북이고 로그 원인 확정은 하지 않습니다.
- 속도나 비용도 좋아졌나요? 새 RAG·자율 협업 비교 실험은 하지 않았습니다. API14호출은 사용 기록이며 비용 개선 지표가 아닙니다.

## 증거 부록
