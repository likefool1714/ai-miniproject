# Canva 구성에 맞춘 5분 발표 대본

표지 포함 9장, 총 목표 300초. 실제 발표 시간은 연습으로 확인한다.
화면에는 핵심 문장과 짧은 코드만 두고 아래 설명은 말로 전달한다.
이름 `G028 최민석`은 표지 좌측 하단에만 작게 표기한다. 본문에는 이름이나 발표 날짜를 반복하지 않는다.

## 1. 표지 — 운영 장애 대응 에이전트 - 15초

안녕하세요. G028 최민석입니다. 과제 1번으로 제공된 운영 장애 대응 에이전트를 개선했습니다.
오늘은 상태 변화 추적과 근거 기반 복구 확인을 중심으로, 기존 코드에서 무엇을 바꿨고 어떻게 확인했는지 말씀드리겠습니다.

## 2. 기존 구조 - 25초

기존에는 질문을 받으면 LLM이 조사 계획을 만들고, MCP로 모니터링과 런북을 조회한 뒤 답변했습니다.
보이는 코드는 기존 검증의 핵심 한 줄입니다. 답변 길이와 번호 형식을 검사하지만, 그 내용이 실제 근거와 맞는지까지 확인하는 조건은 아니었습니다.

코드 근거: 제공 코드 `d1043ff`의 `agent/graph.py`, validate_node.

## 3. 추가한 처리 - 25초

모델·MCP·웹 연결은 제공 코드를 재사용했습니다.
여기에 조사 대상을 확인하고, 서비스 관측을 저장해 이전 상태와 비교하는 흐름을 추가했습니다.
복구와 재발은 코드 정책으로 판단하고, 일반 진단은 모델이 선택한 근거와 런북 항목을 검사한 뒤 설명하도록 바꿨습니다.
기존 대화 저장과 새로 추가한 서비스 관측 저장은 구분했습니다.

코드 근거: recovery_nodes.py, recovery_store.py, recovery.py, grounding.py, graph.py.

## 4. 발견한 문제 - 30초

실행 기록에서 세 가지 문제를 확인했습니다.
첫째, 현재 수치가 한 번 정상으로 돌아왔다고 복구를 확정하는 경우가 있었습니다.
둘째, 후속 질문에서 이전 조사 대상이 유지되지 않는 경우가 있었습니다.
셋째, 실제 조회하지 않은 로그나 점검을 확인한 것처럼 답변하는 경우가 있었습니다.
그래서 상태의 연속성, 조사 대상, 답변 근거를 함께 보완했습니다.

근거: results/baseline-2026-10-20/, results/recovery-2026-10-20/, results/qa-comparison-2026-10-21/.

## 5. 정상 1회와 복구의 차이 - 30초

이 사례는 합성 모니터링입니다. 장애가 있던 결제 서비스에서 CPU 55%, 메모리 60%, 알림 0건이 처음 관측됐습니다.
원본은 현재 상태 기준 복구 완료라고 답했습니다.
현재 수치는 정상이지만 정상 관측은 아직 한 번입니다.
제가 바꾼 부분은 이전 장애 기록과 간격을 둔 정상 관측을 확인해, 일시적인 정상화와 복구 확인을 구분하도록 한 것입니다.

슬라이드 왼쪽은 입력·답변의 요약이며 실제 JSON 스키마가 아니다. 실제 답변은 짧은 발췌다.
근거: results/recovery-2026-10-20/manual-review.json, responses.json.

## 6. 판정과 근거 검증 - 45초

여기는 실제 구현에서 발췌한 코드입니다.
왼쪽은 유효한 정상 관측을 세는 부분입니다. 전체 함수에서는 상태·수치·알림, 관측 중복과 유효시간, 간격을 확인합니다.
교육용 기본 정책으로 최근 장애 이후 정상 관측 두 번과 최소 5초 간격이 있어야 복구로 표시합니다.
가운데는 모델의 제안을 검증 함수로 넘기는 부분입니다. 실제 관측·런북과 맞는 근거인지 검사합니다.
오른쪽은 재작성 횟수 조건입니다. 한 번만 재작성하고 다시 실패하면 보류합니다.
모델은 계획과 진단 항목을 선택하고, 코드가 수치와 채택 조건을 검사하도록 역할을 나눴습니다.

발췌 위치: recovery.py의 normal_streak 증가, graph.py의 validate_draft 호출과 attempts < 2 조건. validate_draft 구현은 grounding.py.
코드 조각은 별도 위치의 핵심 발췌이며 하나의 실행 가능한 함수 전체가 아니다.

## 7. 개선 전후 - 60초

같은 질문과 다섯 단계의 고정 관측을 원본과 개선 코드에 넣고 세 번 반복했습니다.
정상 한 번만으로 잘못 복구를 확정한 횟수는 세 번에서 영 번으로 줄었습니다.
반대로 필요한 재발 안내는 영 번에서 세 번으로 늘었습니다. 그래서 두 지표는 좋아지는 숫자 방향이 다릅니다.
이후 설명 보완 버전의 실제 로컬 웹에서도 세 주기의 열다섯 상태 판정이 기대 결과와 일치했습니다.
제공 API로 전환한 별도 검사에서는 일반 진단 POST 세 건과 SSE 한 건이 근거 검증을 통과했고, 복구 흐름과 이력·보고서도 확인했습니다.
같은 제한된 시나리오와 기능 호환 검사이므로 전체 장애 진단 정확도라고 확대하지 않았습니다.

근거: results/recovery-2026-10-20/, results/revalidation-2026-10-21/, results/api-2026-10-21/.

## 8. 조사 기록의 연결 - 45초

사용자가 쓸 수 있는 기능은 서비스별 조사 이력, 이전·현재 수치와 알림 비교, 새 관측을 가져오는 복구 재점검, 복구 이후 재발 감지, Markdown 보고서입니다.
“그 서비스 다시 확인해줘”라고 하면 같은 대화의 이전 대상을 이어받습니다. 대상이 모호하면 확인 질문을 합니다.
이력과 보고서는 저장한 자료를 읽고, 재점검은 새 자료를 조회한다는 차이가 있습니다.
주기적 자동 감시나 재시작·확장 같은 운영 조치를 실행하는 기능은 아닙니다.

코드 근거: recovery_nodes.py, recovery_store.py, recovery.py, server.py, web_chat.html.

## 9. 한계와 다음 단계 - 25초

샘플 데이터로 확인했으므로 실제 결제 성공이나 근본 원인 제거는 검증하지 않았습니다.
정상 두 번을 요구하면 신중해지는 대신 복구 확인이 늦어집니다. 기준은 실제 운영 적용 시 서비스별로 조정해야 합니다.
제공 API는 확인했고 LangSmith 실제 추적은 미검증입니다.
실제 지표 연결과 관련 서비스·변경 이력 조사는 후속 과제로 구분했습니다. 감사합니다.

## 질문 대비

- 왜 규칙인가요? 같은 수치의 복구 판단을 일정하게 하기 위한 선택입니다. LLM은 계획·진단 항목 선택에 사용합니다.
- 정상 2회가 표준인가요? 교육용 정책입니다. 실제 운영에서는 SLO와 관측 주기로 정해야 합니다.
- 검증 통과면 전부 정확한가요? 확보한 자료와 선택한 항목의 일관성을 검사하며 근본 원인·일반 대화까지 보장하지 않습니다.
- 원본도 오늘 전체 재검증했나요? 과거 전후 비교와 최신 개선 코드 전체 재검증은 별도입니다. 최신 전체 검사에서 원본을 다시 실행하지 않았습니다.
