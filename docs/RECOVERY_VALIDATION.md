- 일시 정상 이후 악화를 확인된 복구 이후 재발과 구분
- 동일 관측 중복·ID 내용 충돌, 순서 역전, 오래된/미래/미확인/범위 밖·NaN/무한대 자료

API 통합의 LLM은 fake다. MCP는 실제 프로세스·프로토콜을 사용한다. 이 검사는 실제 모델의 자연어 품질 검사가 아니다.

## 2. 고정 조건 원본/개선 비교

실행: `.venv/bin/python eval/compare_recovery.py --backend ollama --repetitions 3`

- 원본: 커밋 `d1043ff`의 실제 LangGraph 코드
- 모델: 로컬 Ollama qwen3:0.6b / qwen3:8b
- 입력: `payments-service의 복구 여부를 진단해 주세요`
- 같은 5개 관측과 고정 시계, 각 버전·대화별 3회 반복 (원본 15, 개선 15)
- MCP I/O는 같은 고정 fixture를 주입. 실제 MCP/HTTP 지연은 이 수치에 포함하지 않음
- 원본은 기존 LLM 진단, 개선은 새 코드 기반 복구 경로 사용

| 단계 | 관측 | 기대 판정 |
|---|---|---|
| 1 | degraded, CPU 95, 메모리 90, 알림 2 | 장애 지속 |
| 2 | degraded, CPU 65, 메모리 87, 알림 1 | 부분 회복 |
| 3 | healthy, CPU 55, 메모리 60, 알림 0 | 부분 회복 (정상 1회) |
| 4 | healthy, CPU 54, 메모리 58, 알림 0 | 복구 확인 (정상 2회) |
| 5 | degraded, CPU 94, 메모리 60, 알림 1 | 장애 지속 + 재발 |

| 지표 | 원본 | 개선 |
|---|---|---|
| 응답 완료 | 15/15 | 15/15 |
| 단계 3에서 조기 복구 확정 | 3/3 | 0/3 |
| 단계 5에서 재발 명시 | 0/3 | 3/3 |
| 정책 판정·기대 결과 일치 | 자연어 원문 별도 검토 | 15/15 |
| 그래프 지연 중앙값 | 28.7905초 | 0.002908초 |

원본 단계 3의 답변은 “현재 상태 기준 복구 완료”라고 명시했다. 개선은 정상 1/2회이므로 보류 이유를 표시했다.
원본 단계 5는 현재 CPU 과부하 지속을 설명했고 이전 복구 이후 재발임을 명시하지 않았다.
구조화 판정이 없다는 이유만으로 원본 자연어를 자동 오답 처리하지 않았다. 전체 자연어 정확도는 산출하지 않는다.
이 세 번은 같은 5개 관측 세트를 반복한 것이며 서로 다른 장애 15개를 검증한 것이 아니다.

원문: `responses.json`, 집계: `summary.json`, 원문 대조: `manual-review.json`.
모두 `results/recovery-2026-10-20/`에 보존한다.

## 6. 사용자 요청에 따른 전체 경로 재확인

실행 중인 최종 서버에서 첫 요청을 `payments-service 장애를 진단해주세요`로 보내 기존 Ollama 진단 경로까지 실행했다.
첫 진단은 약 39.65초에 완료했고, 이후 같은 대화에서 서비스명을 생략한 재점검 4회는 부분 회복·부분 회복·복구 확인·재발로 진행했다.
조사 이력은 5건이며, 이력·보고서 조회로 관측이 늘지 않았고 Markdown 다운로드가 성공했다.
단위·API 검사 20개도 다시 통과했다.

**남은 문제:** 첫 일반 진단의 LLM 답변에 “최근 로그 및 패턴 분석에서 특이한 요청 패턴은 발견되지 않았습니다”라는 미수집 로그 분석 주장이 다시 관측됐다.
새 정책 기반 복구 판정은 동작했지만 기존 Writer의 모든 근거 오류를 해결한 상태는 아니다.
따라서 최종 등록 10개 항목의 기능 동작과 일반 진단 답변 전체의 정확성을 구분한다.
